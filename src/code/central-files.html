Purpose

{{link code/index | The folder tree}} lists every folder. This page picks the 19 files inside src/ that carry most of the project's own logic, and gives each one's size, role and main export. Every concept page on this site walks through some of these files in detail; this page is the map you come back to, not a replacement for reading them.

The domain core (src/core/)

These seven files are the whole domain core, which {{link code/index}} already showed imports nothing outside itself. Only a few of its exports leave through its own barrel file, src/core/index.ts ({{cite src/core/index.ts:2-9}}); the rest are internal to the Engine.

FileLinesWhat it is
{{cite src/core/model.ts | src/core/model.ts}}353The domain types every other file imports, and nothing else ({{cite src/core/model.ts:1}}): {{term trigger | Trigger}} ({{cite src/core/model.ts:23-39}}), {{term thread | Thread}} ({{cite src/core/model.ts:157-182}}), {{term ticket | Ticket}} ({{cite src/core/model.ts:277-308}}), {{term mandate | Mandate}} ({{cite src/core/model.ts:126-133}}), {{term decision | Decision}} ({{cite src/core/model.ts:190-209}}).
{{cite src/core/engine.ts | src/core/engine.ts}}270The Engine class ({{cite src/core/engine.ts:24}}): the single entry point of the core, and the only part of the code that changes a Trigger, Thread, Decision, Ticket or Assignment ({{cite src/core/engine.ts:19-20}}). It also exports the role-scoped interfaces other layers receive, such as EngineForExecutor ({{cite src/core/engine.ts:269-270}}).
{{cite src/core/tickets.ts | src/core/tickets.ts}}423The Tickets class ({{cite src/core/tickets.ts:29}}): a Ticket's life from an accept to its end, its {{term subscription | Subscriptions}} and its Inputs. The largest file in the core.
{{cite src/core/evals.ts | src/core/evals.ts}}340The Evals class ({{cite src/core/evals.ts:27}}): the Thread-level assessment of queued Triggers, ending in a Decision.
{{cite src/core/assignments.ts | src/core/assignments.ts}}140The Assignments class ({{cite src/core/assignments.ts:30}}) and the WorkerReport shape ({{cite src/core/assignments.ts:11-19}}): what the Executor and its workers report back, and how a Report ends or restarts an Assignment.
{{cite src/core/intake.ts | src/core/intake.ts}}63The Intake class ({{cite src/core/intake.ts:16}}): Trigger ingestion, Thread correlation, Subscription fan-out, and Eval queuing, in that order.
{{cite src/core/ports.ts | src/core/ports.ts}}134The ports (interfaces) the Engine depends on, so the core never imports a Source, a Policy or an Executor directly: Policy ({{cite src/core/ports.ts:17-27}}), Assessor ({{cite src/core/ports.ts:49-53}}), Executor ({{cite src/core/ports.ts:59-69}}), Outbox ({{cite src/core/ports.ts:76-83}}) and Repositories ({{cite src/core/ports.ts:106}}).

Also in src/core/, each small enough that this page does not give it its own row: stage.ts, the {{term stage | stage}} machine ({{cite src/core/stage.ts:9-21}}, walked through step by step on {{link concepts/ticket-lifecycle}}); replies.ts and part.ts (the shared EnginePart base class {{cite src/core/part.ts}}); and three small support files, errors.ts, reasons.ts and ids.ts.

Policy (repository root)

src/policy.ts sits outside src/core/, next to the Engine, not inside it: the Policy it builds is one of the Engine's ports, not part of the domain core itself.

FileLinesWhat it is
{{cite src/policy.ts | src/policy.ts}}242The settings schemas by block (PolicyConfigSchema, EvalConfigSchema, ExecutorConfigSchema, {{cite src/policy.ts:79-97}}), the Policy version ({{cite src/policy.ts:116-118}}), and settingsPolicy() ({{cite src/policy.ts:167-242}}), which builds the gate and Mandate revalidation covered on {{link concepts/policy-and-authorization}}.

Two small files it depends on: src/admission.ts (13 lines, the admission table's own value type, {{cite src/admission.ts:9-13}}) and src/limits.ts (11 lines, the numeric bounds every settings schema checks against, {{cite src/limits.ts:2-11}}).

Execution (src/executor/)

FileLinesWhat it is
{{cite src/executor/dsh.ts | src/executor/dsh.ts}}673The DshExecutor class ({{cite src/executor/dsh.ts:207}}), the only {{term executor | Executor}} this repository registers. It implements the Executor port from ports.ts, and also holds WorkerSlots ({{cite src/executor/dsh.ts:171-199}}), the concurrency limit covered on {{link concepts/executor-and-worker-sessions}}. The largest file in the repository.
{{cite src/executor/background.ts | src/executor/background.ts}}165Functions, not a class: runningJobs(), killJobs() and stopSubagents() manage a worker's shell jobs and subagents in DSH ({{cite src/executor/background.ts:1-3}}), called by dsh.ts to enforce the 30-minute background-work limit.

The app layer (src/app/)

src/app/ is the glue: it gives the Engine its Store and ports, and gives the panel and the CLI a Management API. src/app/runtime.ts (254 lines) is its composition root: Runtime builds the Store ({{cite src/app/runtime.ts:98}}), the Settings ({{cite src/app/runtime.ts:126}}), the DshExecutor ({{cite src/app/runtime.ts:128}}) and the Sessions ({{cite src/app/runtime.ts:121}}), then registers the HTTP routes ({{cite src/app/runtime.ts:203}}). This page gives the six files it wires together their own rows; runtime.ts itself is mostly wiring, so it does not get one.

FileLinesWhat it is
{{cite src/app/store.ts | src/app/store.ts}}291The Store class ({{cite src/app/store.ts:51}}), implementing the core's Repositories port: the one SQLite database behind every domain aggregate, the {{term effect | effect}} queue and the {{term outbox | Outbox}}'s receipts ({{cite src/app/store.ts:46-50}}).
{{cite src/app/effects.ts | src/app/effects.ts}}161The Effects class ({{cite src/app/effects.ts:46}}): the durable queue behind launches, deliveries and replies, with exactly one handler per kind ({{cite src/app/effects.ts:11-24}}, {{cite src/app/effects.ts:67-68}}).
{{cite src/app/sessions.ts | src/app/sessions.ts}}352The Sessions class ({{cite src/app/sessions.ts:93}}): lifecycle, prompt and tool decoration, message delivery and budget-retry tracking for both the main Session and worker Sessions. Also names the two agent presets, WORKER_PRESET and ROUTER_PRESET ({{cite src/app/sessions.ts:48}}).
{{cite src/app/prompts.ts | src/app/prompts.ts}}247The Prompts class ({{cite src/app/prompts.ts:135}}) and promptParts() ({{cite src/app/prompts.ts:102-116}}): versioned role prompts, the fixed join order, and the two bundled {{term source-skill | Source skills}}, covered on {{link concepts/prompts-and-skills}}.
{{cite src/app/settings.ts | src/app/settings.ts}}267The Settings class ({{cite src/app/settings.ts:82}}): block-scoped validation, optimistic-concurrency saves, and the processing-pause control.
{{cite src/app/http.ts | src/app/http.ts}}247registerHttp() ({{cite src/app/http.ts:230-246}}) and routes() ({{cite src/app/http.ts:151-214}}): the loopback-only {{term management-api | Management API}} every route of {{link reference/config-and-deployment}}'s route table comes from.

Also central to the app layer, without a row here because other pages already cite them in full: runtime.ts (above), context.ts (built-in prompt text, {{link concepts/prompts-and-skills}}), outbox.ts and versions.ts (whole-object snapshot saving, {{link concepts/effects-and-store}} and {{link concepts/panel-and-management-api}}), and api.ts (the route table's shared types, read by both the server and the browser bundle, {{cite src/app/api.ts:1}}).

Source plugins (src/sources/)

FileLinesWhat it is
{{cite src/sources/kind.ts | src/sources/kind.ts}}115The SourceKind contract every {{term source | Source}} implements ({{cite src/sources/kind.ts:85-113}}): its configuration schema, its admission-table rows and its outbound Channel adapter.
{{cite src/sources/github.ts | src/sources/github.ts}}459githubKind ({{cite src/sources/github.ts:38}}), the one SourceKind this repository ships two of (the other is Feishu's): the GitHub Source's notification and repository polling loops, and its Cordis plugin entry, name = 'dsh-superagent-github' ({{cite src/sources/github.ts:110-112}}).

src/sources/registry.ts (138 lines) resolves one configured instance of an installed kind and routes an outgoing message to it ({{cite src/sources/registry.ts:50-53}}, {{cite src/sources/registry.ts:95-98}}); src/sources/feishu.ts (139 lines) is GitHub's counterpart for Feishu. Neither gets its own row: their role is the same shape as kind.ts and github.ts above.

The panel's data (src/client/)

FileLinesWhat it is
{{cite src/client/locales.ts | src/client/locales.ts}}770The bilingual {zh, en} UI dictionaries the panel reads, grouped to follow the domain terms of {{cite docs/001-domain.md}} ({{cite src/client/locales.ts:1-3}}). The largest file under src/client/, and the only file this repository's Chinese text lives in besides locale/*.json (out of scope on this site). Pure data: it calls nothing and is called only for its exported dictionaries, zh and en ({{cite src/client/locales.ts:752}}).

The panel's own structure, routes and six tabs are covered in full on {{link concepts/panel-and-management-api}}, which cites src/client/index.tsx, route.ts and api.ts directly. This page does not repeat those files here.
