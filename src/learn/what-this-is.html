The idea

When an allowed person asks dsh-superagent for work, it opens a {{term ticket | Ticket}}. It works on the Ticket in its own agent Session and directory, and it answers in the original conversation ({{cite README.md:7}}). Its guiding rule is to take as little human attention as possible, and give as much value as possible ({{cite docs/000-philosophy.md:5}}). It stays quiet unless a rule allows it to act, or a result needs a person.

An everyday comparison. Think of a new teammate who speaks up only when asked and works alone at their own desk. They report back in the same conversation where the request came from. The comparison stops at authorization. A human teammate uses judgment, but dsh-superagent only ever acts under a written {{term policy | Policy}} ({{cite src/core/ports.ts:17-27}}), never its own judgment of who may ask.

What the sibling site already teaches

This site assumes you already know DSH and Cordis from the sibling site, DeepSeek Harness Explained. It does not re-teach them; each line below only recaps and names the matching page there.

  • Cordis plugins. DeepSeek Harness is built on Cordis, a plugin framework whose plugins share a context and cooperate only through typed events and effects. See the sibling site's page "Everything is a plugin: Cordis".
  • Profiles and bundles. A DSH profile stacks named bundles, then patch files overlay the result, to assemble one running DSH tree. dsh-superagent is one such bundle. See "Profiles and bundles".
  • The session vocabulary. A DSH session counts its own work with four words: turn, step, round and exchange. See "Turn, step, round: the session vocabulary".
  • Skills. A skill is one full instruction body that a session loads on demand from a shared catalog. See "Skills".
  • Jobs and background work. A background job, a workflow script, a durable goal and plan mode are optional capabilities beside the turn/step loop. See "Jobs, workflows, goals and plan mode".

What dsh-superagent adds

{{term source | Source}} and {{term trigger | Trigger}}. A Source is a stream of events, such as the GitHub Source ({{cite src/sources/github.ts:38-64}}). Each event becomes one immutable Trigger, with its own {{term thread | Threads}} and, where relevant, a {{term channel | Channel}} to reply on ({{cite src/core/model.ts:23-39}}). {{link concepts/sources-and-triggers}} covers all four.

{{term policy | Policy}} and {{term eval | Eval}}. A Policy is the versioned rule set that decides who may start work. A gate checks each Trigger against it, and Eval turns an admissible batch into a {{term decision | Decision}} ({{cite src/core/ports.ts:17-27}}, {{cite src/core/evals.ts:21-26}}). An accept Decision carries a {{term mandate | Mandate}}: the {{term strength | strength}}, scope and Policy version the work relies on ({{cite src/core/model.ts:126-133}}). {{link concepts/policy-and-authorization}} covers all five.

{{term ticket | Ticket}}. Only an accept Decision creates a Ticket, and it has no stored status field. Its {{term stage | stage}} is computed fresh each time, from its {{term assignment | Assignments}} and reports ({{cite src/core/model.ts:277-308}}, {{cite src/core/tickets.ts:23-29}}). {{link concepts/ticket-lifecycle}} follows one Ticket from accept to end.

{{term executor | Executor}}. The Executor is the port that runs a Ticket's work: one Executor Session and one directory per Ticket ({{cite src/core/ports.ts:59-69}}). dsh-superagent's own implementation runs that Session inside DSH, under a worker slot limit ({{cite src/executor/dsh.ts:201-207}}). {{link concepts/executor-and-worker-sessions}} covers it, and {{link concepts/effects-and-store}} covers the durable queue and Store behind it.

The panel. A React panel, injected into DSH's web sidebar, shows only what needs a person, and a local {{term management-api | Management API}} backs it ({{cite src/client/app.tsx:1}}). {{link concepts/panel-and-management-api}} covers both, and {{link concepts/prompts-and-skills}} covers the prompts the Executor and the main Session read.

More detail

One Trigger's path through these parts runs in a fixed order.

  1. Intake stores the Trigger and checks the Source's scope ({{cite src/core/intake.ts:19-62}}).
  2. The gate decides the Trigger's strength ({{cite src/policy.ts:191-211}}).
  3. Eval batches the Thread's queued Triggers into one Decision ({{cite src/core/evals.ts:71-119}}).
  4. An accept Decision builds the Ticket and its Mandate ({{cite src/core/tickets.ts:37-56}}).
  5. The Executor launches a worker Session, which can reply through a Channel ({{cite src/executor/dsh.ts:264-266}}).

A later Trigger on a Thread the Ticket already subscribes to skips the gate and Eval entirely. It reaches the Ticket as a new Input through its Subscription instead ({{cite src/core/intake.ts:34-52}}).

Two settings change this path's behaviour the most. The Policy's {{term accept-mode | accept mode}} is off, observe or auto ({{cite src/core/model.ts:103}}). It decides whether an inferred candidate, one not addressed to the agent by an allowed person, can ever become a Ticket. Only auto lets a positive assessment accept one ({{cite src/core/ports.ts:24}}). The Executor's maxWorkers limit decides how many Tickets can have a running worker Session at once ({{cite src/executor/dsh.ts:229-230}}).

GitHub and Feishu are two different Source kinds. Both implement the same SourceKind contract: a configuration schema, a scope function that decides what the Source listens to, and a channel to reply on ({{cite src/sources/kind.ts:85-100}}). Policy and Eval never see a Source's own vocabulary, such as a Feishu chat or a GitHub Issue. They see only Triggers, Threads and Channels. This is why {{link concepts/sources-and-triggers}} explains one shared model, instead of one page per Source.

For the full domain model and why each concept exists, see the repository's own {{cite docs/001-domain.md}}.

What can go wrong

Source, Trigger, Policy, Eval, Ticket and Executor are deliberately abstract. A business need becomes an attribute of one of them, or prompt text, never a new concept ({{cite docs/001-domain.md:3}}). Looking for "the Feishu-specific rule" inside the domain layer is looking in the wrong place. It lives in the Feishu Source, and in prompts.
  • "Executor" and "worker" are not interchangeable with "Ticket." The Executor is the port that runs the work; the worker is its Session, named worker-<ticket id> ({{cite src/executor/dsh.ts:24}}). A Ticket itself is never called a worker.
  • The main Session is not a Ticket's worker. Code and prompts name the two roles orchestrator and worker ({{cite src/app/prompts.ts:46}}). The main Session routes and accepts work. Only an Executor Session does the ticketed work itself.

Why it matters. Mixing up these roles makes it easy to look for a Ticket's own behaviour inside the Executor's code. The mistake also runs the other way round.

Does dsh-superagent re-implement Cordis plugins or DSH profiles itself?

No. It runs as one DSH bundle, a Cordis plugin set a DSH profile loads ({{cite src/index.ts:1-7}}); Cordis and DSH profiles are the sibling site's own territory.

 Which concept does only an accept Decision ever create?

A Ticket. {{cite src/core/model.ts:277-308}}'s own rules, read with {{cite src/core/tickets.ts:37-56}}, show that nothing else creates one.

 A later GitHub comment on a Thread a Ticket already follows arrives. Does it go through the gate and Eval again?

No. {{cite src/core/intake.ts:34-52}} fans it out to the subscribed Ticket directly, as a new Input, with no new Eval or Decision.

 Why does the domain model have no Feishu-specific or GitHub-specific concept?

Every Source implements one shared contract, {{cite src/sources/kind.ts:85-100}}: Policy and Eval only ever see Triggers, Threads and Channels. A business need specific to one Source becomes an attribute of that Source, or prompt text, never a new domain concept ({{cite docs/001-domain.md:3}}).
