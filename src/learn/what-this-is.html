The idea

When an allowed person asks dsh-superagent for work, it opens a {{term ticket | Ticket}}. It works on the Ticket in its own agent Session and directory, and it answers in the original conversation ({{cite README.md:7}}). Its guiding rule is to take as little human attention as possible, and give as much value as possible ({{cite docs/000-philosophy.md:5}}). It acts only when a person asks, or when a rule that the team wrote allows it. It speaks only when a person must act or can use a result ({{cite README.md:9}}).

An everyday comparison. Think of a new teammate who speaks up only when asked and works alone at their own desk. They report back in the same conversation where the request came from. The comparison stops at authorization. A human teammate uses judgment, but a written {{term policy | Policy}} decides who may ask dsh-superagent for work ({{cite src/core/ports.ts:16-20}}). The agent does not use its own judgment for this.

In dsh-superagent

What the sibling site already teaches

This site assumes you already know DSH and Cordis from the sibling site, DeepSeek Harness Explained. It does not re-teach them; each line below only recaps and names the matching page there.

  • Cordis plugins. In DeepSeek Harness, every part is a plugin on Cordis. A plugin claims services from a shared context, and plugins tell each other about events. See the sibling site's page "Everything is a plugin: Cordis".
  • Profiles and bundles. A {{term dsh-profile | DSH profile}} stacks named bundles, then patch files overlay the result, to assemble one running DSH tree. dsh-superagent is one such {{term dsh-bundle | bundle}}. See "Profiles and bundles".
  • The session vocabulary. A DSH session counts its own work with four words: turn, step, round and exchange. See "Turn, step, round: the session vocabulary".
  • Skills. A skill is one full instruction body that a session loads on demand from a shared catalog. See "Skills".
  • Jobs and background work. A background job, a workflow script, a durable goal and plan mode are optional capabilities beside the turn/step loop. See "Jobs, workflows, goals and plan mode".

What dsh-superagent adds

{{term source | Source}} and {{term trigger | Trigger}}. A Source is a stream of events, such as the GitHub Source ({{cite src/sources/github.ts:38-64}}). Each event becomes one immutable Trigger, with its own {{term thread | Threads}} and, where relevant, a {{term channel | Channel}} to reply on ({{cite src/core/model.ts:22-39}}). {{link concepts/sources-and-triggers}} covers all four.

{{term policy | Policy}} and {{term eval | Eval}}. A Policy is the versioned rule set that decides who may start work. A gate checks each Trigger against it, and Eval turns an admissible batch into a {{term decision | Decision}} ({{cite src/core/ports.ts:17-27}}, {{cite src/core/evals.ts:21-26}}). An accept Decision carries a {{term mandate | Mandate}}: the {{term strength | strength}}, scope and Policy version the work relies on ({{cite src/core/model.ts:125-133}}). {{link concepts/policy-and-authorization}} covers all five.

{{term ticket | Ticket}}. Only an accept Decision creates a Ticket ({{cite src/core/evals.ts:306-316}}). The Ticket has no stored status field ({{cite src/core/model.ts:277-308}}). Its {{term stage | stage}} is computed each time from its stored facts, mainly its latest {{term assignment | Assignment}} and that Assignment's Report ({{cite src/core/stage.ts:9-21}}). {{link concepts/ticket-lifecycle}} follows one Ticket from accept to end.

{{term executor | Executor}}. The Executor is the port that runs a Ticket's Assignments ({{cite src/core/ports.ts:55-69}}). dsh-superagent's own implementation keeps one worker Session and one directory for each Ticket ({{cite src/executor/dsh.ts:1}}). It runs that Session inside DSH, under a worker slot limit ({{cite src/executor/dsh.ts:201-207}}). {{link concepts/executor-and-worker-sessions}} covers it, and {{link concepts/effects-and-store}} covers the durable queue and Store behind it.

The panel. A React panel opens from an icon in DSH's web sidebar ({{cite src/client/index.tsx:49-55}}). It shows what needs a person ({{cite README.md:7}}). A local {{term management-api | Management API}} serves its data ({{cite src/app/http.ts:230-237}}). {{link concepts/panel-and-management-api}} covers both, and {{link concepts/prompts-and-skills}} covers the prompts the Executor and the main Session read.

More detail

One Trigger's path through these parts runs in a fixed order.

  1. Intake stores the Trigger, checks the Source's scope, and fans the Trigger out to subscribed Tickets ({{cite src/core/intake.ts:19-62}}).
  2. When no Ticket's worker decides the Trigger, it goes to Eval. The gate decides its strength ({{cite src/core/intake.ts:58}}, {{cite src/policy.ts:191-211}}).
  3. Eval batches the Thread's queued Triggers into one Decision ({{cite src/core/evals.ts:71-119}}).
  4. An accept Decision builds the Mandate and the Ticket ({{cite src/core/evals.ts:306-316}}, {{cite src/core/tickets.ts:37-56}}).
  5. The Executor queues a launch of a worker Session ({{cite src/executor/dsh.ts:263-266}}). A reply goes out through a Channel ({{cite src/app/outbox.ts:26-32}}).

A later Trigger on a Thread that a live Ticket subscribes to reaches the Ticket as a new Input through its Subscription ({{cite src/core/intake.ts:34-52}}). When the Ticket's worker decides a person's message, the message goes to no Eval. A bot's message goes to Eval too ({{cite src/core/intake.ts:56-58}}).

Two settings change this path's behaviour the most. The Policy's {{term accept-mode | accept mode}} is off, observe or auto ({{cite src/core/model.ts:103}}). It decides whether an inferred candidate can become a Ticket. The gate marks a candidate inferred when it is not an explicit request. Only auto lets an assessment accept an inferred candidate, and only on enabled rules that the assessment matched ({{cite src/policy.ts:212}}). The Executor's maxWorkers limit decides how many worker Sessions can run at once ({{cite src/executor/dsh.ts:229-230}}). A wake for a person's message can use one extra slot ({{cite src/executor/dsh.ts:192-194}}).

GitHub and Feishu are two different Source kinds. Both implement the same SourceKind contract ({{cite src/sources/kind.ts:85-100}}). The contract has a configuration schema. Its optional parts include a scope function that decides what the Source listens to, and a channel to reply on. Policy and Eval never see a Source's own vocabulary, such as a Feishu chat or a GitHub Issue. They see only Triggers, Threads and Channels. This is why {{link concepts/sources-and-triggers}} explains one shared model, instead of one page per Source.

For the full domain model and why each concept exists, see the repository's own {{cite docs/001-domain.md}}.

What can go wrong

Source, Trigger, Policy, Eval, Ticket and Executor are deliberately abstract. A business need becomes an attribute of one of them, or prompt text, never a new concept ({{cite docs/001-domain.md:3}}, {{cite docs/001-domain.md:39}}). Do not look for a Feishu-specific rule in the domain layer. Look in the Feishu Source and in the prompts.
  • "Executor" and "worker" are not interchangeable with "Ticket." The Executor is the port that runs the work; the worker is its Session, named worker-<ticket id> ({{cite src/executor/dsh.ts:24}}). A Ticket itself is never called a worker.
  • The main Session is not a Ticket's worker. Code and prompts name the two roles orchestrator and worker ({{cite src/app/prompts.ts:46}}). The main Session evaluates Triggers, accepts and dispatches Tickets, and replies ({{cite docs/001-domain.md:80-81}}). Only an Executor Session does the ticketed work itself.

Why it matters. If you mix up these roles, you can look for a Ticket's own behaviour in the Executor's code. You can also make the opposite mistake.

Does dsh-superagent re-implement Cordis plugins or DSH profiles itself?

No. It runs as one DSH bundle, a set of Cordis plugins that a DSH profile loads ({{cite cordis.patch.yml:4-12}}). Cordis and DSH profiles are the sibling site's own territory.

 Which concept does only an accept Decision ever create?

A Ticket. Tickets.create() ({{cite src/core/tickets.ts:37-56}}) has one caller, Evals.accept() ({{cite src/core/evals.ts:306-316}}).

 A person writes a later GitHub comment on a Thread that a live Ticket subscribes to. Does the comment go through the gate and Eval again?

No, when the Ticket's worker decides the comment. {{cite src/core/intake.ts:34-52}} fans it out to the subscribed Ticket directly, as a new Input, with no new Eval or Decision. Only a Trigger that no Ticket's worker decides goes to Eval ({{cite src/core/intake.ts:58}}).

 Why does the domain model have no Feishu-specific or GitHub-specific concept?

Every Source implements one shared contract, {{cite src/sources/kind.ts:85-100}}: Policy and Eval only ever see Triggers, Threads and Channels. A business need specific to one Source becomes an attribute of that Source, or prompt text, never a new domain concept ({{cite docs/001-domain.md:3}}, {{cite docs/001-domain.md:39}}).
