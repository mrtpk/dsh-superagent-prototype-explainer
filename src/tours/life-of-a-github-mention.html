The idea

This tour follows one real path through the system map on the home page: a comment that mentions dsh-superagent's GitHub account. Every stop below names the file and the function the reader is in, with the exact lines.

An everyday comparison. Think of an email that reaches a busy person's inbox. Someone checks whether the sender may ask for this kind of work, and decides to accept it. Only then do they start, reply and, at the end, close it. The comparison stops at the gate: dsh-superagent's check is a written rule in code, not a person's judgment.

The picture

Read each panel left to right. The three parts match this tour's stops in groups: stops 1-7 build the Ticket, stops 8-11 do the work, and stops 12-13 end the Ticket.

The GitHub {{term source | Source}} reads the comment in a poll, and turns it into a {{term trigger | Trigger}}. mentions() matches @login only as a whole name, and ignores upper and lower case.

For a mention, the notification poll reads the Issue or pull request that GitHub names ({{cite src/sources/github.ts:344-372}}). It calls intakeComments(), which reads the comments since the Thread's cursor and passes each to ctx.receive() ({{cite src/sources/github.ts:384-402}}). The poll of a subscribed Thread also calls intakeComments() ({{cite src/sources/github.ts:452-457}}).

Intake.receive() normalizes the timestamp, rejects a duplicate id, and checks the Source's scope before the Trigger enters the domain.

Because no Ticket yet subscribes to this comment's {{term thread | Thread}}, the fan-out loop reaches none ({{cite src/core/intake.ts:34-48}}), and the Trigger is queued for {{term eval | Eval}} ({{cite src/core/intake.ts:58}}).

Before Eval batches anything, the active {{term policy | Policy}}'s gate decides the {{term strength | strength}} of every queued Trigger on the Thread. For a human Trigger, an allowed sender who addressed the agent is always explicit.

{{cite src/core/evals.ts:96}} calls this gate once per queued Trigger when Evals.start() runs on the Thread.

Evals.start() takes every Trigger still queued on the Thread, keeps the strongest admissible one, and opens one Eval for the whole batch.

assessor.request() enqueues an assessment {{term effect | effect}}. Its handler delivers the candidate card to the main Session ({{cite src/app/assessment.ts:96-104}}). This happens for an explicit candidate too. But the assessment tools orchestrator_eval and orchestrator_eval_read refuse an explicit candidate. Their error tells the main Session to route it with orchestrator_route ({{cite src/app/assessment.ts:39}}, {{cite src/app/assessment.ts:109-113}}). {{cite docs/002-authorization.md:85}} gives the same rule.

orchestrator_route lets the main Session decide several candidates in one call. Each item runs as its own Engine command, so one refused item never blocks the others.

engine.decide() records a {{term decision | Decision}}. Only an accept Decision makes a Ticket. Any other Decision becomes the item's refusal (line 100).

{{cite src/app/tools/main.ts:125-153}} defines the tool itself: up to 20 decisions per call, each answered on its own ({{cite src/app/tools/main.ts:129}}).

Evals.decide() routes the accept outcome to accept(), which builds the {{term mandate | Mandate}} the new Ticket will carry.

The Ticket's id comes from the Eval's own id ({{cite src/core/evals.ts:311}}). Thus one Eval maps to one Ticket id. Evals.decide() also returns the earlier Decision when a Trigger already made a Ticket ({{cite src/core/evals.ts:136-146}}).

Tickets.create() does four things in one call. It builds the Ticket and its first {{term assignment | Assignment}}. It subscribes the Ticket to every Thread of the Eval's Triggers. It queues the accept's acknowledgement, when the accept has one, and asks the {{term executor | Executor}} to start.

Ticket creation is covered in full on {{link concepts/ticket-lifecycle}}. This tour only follows the one path this mention takes.

Because the comment's Trigger is human and has a {{term channel | Channel}}, the accept's acknowledgement is queued for delivery before the worker even starts.

The {{term outbox | Outbox}} records a receipt and enqueues a durable reply effect in the same transaction ({{cite src/app/outbox.ts:27-32}}). Later, sendGithub() posts the comment under the agent's account. A hidden marker in the comment lets a retry find the earlier post, so the retry does not post it again ({{cite src/sources/github-channel.ts:34-39}}).

DshExecutor.start() only enqueues a launch effect; the actual launch runs once a {{term worker-slot | worker slot}} is free.

launch() prepares the Ticket's workspace directory on first use ({{cite src/executor/dsh.ts:434-438}}), then sends the first message with the Ticket's assignment text and the originating Trigger ({{cite src/executor/dsh.ts:449-466}}).

A launch only runs once WorkerSlots.reserve() grants it a slot ({{cite src/executor/dsh.ts:192-194}}). The limit comes from the Executor's maxWorkers setting ({{cite src/executor/dsh.ts:229-230}}). Until then, the Assignment stays pending, and the panel shows the Ticket as "Queued" ({{cite src/core/stage.ts:18}}, {{cite docs/003-execution.md:15}}). A launch never gets an extra slot. A wake of an idle worker for a person's message, or for a status request, may use one extra slot beyond the limit ({{cite src/executor/dsh.ts:38}}, {{cite src/executor/dsh.ts:305-308}}). Thus a busy deployment can still answer a person who talks to an existing Ticket.

The worker reads its assignment and the Ticket's execution variables. They name the repository, the agent's GitHub account, and the Issue or pull request that started the Ticket.

The worker gets these variables as a list in its system prompt, not as shell variables ({{cite src/app/sessions.ts:247}}, {{cite src/app/prompts.ts:83-84}}). dsh-superagent knows a pull request of the worker by its author and its branch name. The agent account must be the author, and the branch's last path segment must match the Ticket's short name ({{cite src/sources/github-pull.ts:23-28}}). {{cite docs/003-execution.md:53}} describes the same contract.

orchestrator_report is how a worker tells its Ticket what happened. Naming a pr_number claims that pull request for the Ticket in the same call.

claimPull() accepts only the Ticket's own source PR, or an agent-authored PR on the Ticket's branch, and refuses a PR another open Ticket already claims ({{cite src/sources/github-pull.ts:35-49}}).

Assignments.report() stores the worker's {{term report | report}} on the Assignment, and decides whether this report ends the Ticket.

With an open pull request still followed, this ready report leaves the Ticket open, in the stage person / review ({{cite src/core/stage.ts:15}}). The panel calls this stage "Awaiting review" ({{cite docs/003-execution.md:13}}).

Each poll round reads the open pull requests that open Tickets follow ({{cite src/sources/github.ts:404-409}}). Once a pull request is closed or merged, observePull() reports it to the Tickets that follow it.

Tickets.threadClosed() marks the follow closed. It ends the Ticket when followsDone() holds and no taken-up work is unfinished ({{cite src/core/tickets.ts:77-89}}, {{cite src/core/tickets.ts:345-362}}). followsDone() holds once every pull request that the Ticket opened is closed. For a Ticket that opened none, every followed Thread must close ({{cite src/core/tickets.ts:95-100}}). GitHub already shows the merge or close on the pull request itself, so the final notice this Ticket would otherwise send skips its GitHub Channels ({{cite src/sources/github-pull.ts:102-104}}).

What can go wrong

Check whether the Ticket still follows an open pull request before reading a ready report as finished work. {{cite src/core/assignments.ts:128-132}} ends the Ticket only once followsDone() has an outcome, which an open, followed pull request does not yet have.
  • An inferred mention would not take this path. This tour assumes an allowed sender's explicit mention. A person not on the allowed list, or a comment that does not mention the agent, takes the admission-table path instead ({{cite src/policy.ts:198-210}}). An inferred candidate from that path becomes a Ticket only in auto mode ({{cite docs/002-authorization.md:91-101}}).
  • A later comment by a person on the same Thread does not repeat this tour. Once the Thread's Ticket exists, the Trigger reaches it through its Subscription ({{cite src/core/intake.ts:34-52}}). The Ticket owns the Trigger, so it gets no new Eval ({{cite src/core/intake.ts:56-58}}). A bot's comment still goes to Eval ({{cite src/core/model.ts:76}}).

Why it matters. Do not read every comment as a new "mention to Ticket" run. Only the first request on a Thread takes this full path. The worker decides a later comment by a person, not the gate.

Which function decides that an allowed person's mention is explicit, not inferred?

The Policy's gate, {{cite src/policy.ts:191-211}}. Line 197 returns explicit strength once an allowed sender's Trigger is addressed.

 Does the acknowledgement reply wait for the worker to start?

No. {{cite src/core/tickets.ts:49-56}} queues the acknowledgement in the same call that creates the Ticket, before the Executor's launch even reaches a worker slot.

 How does dsh-superagent know a pull request belongs to this Ticket, if the worker opened it itself?

By its branch name. {{cite src/sources/github-pull.ts:27-28}}'s ticketBranch() matches the branch's last path segment against the Ticket's short name, which claimPull() then checks when the worker reports it ({{cite src/sources/github-pull.ts:35-49}}).

 A worker reports ready with an open pull request it is still following. Does the Ticket end?

No. {{cite src/core/assignments.ts:128-132}} only ends the Ticket once followsDone() gives it an outcome. That needs every pull request the Ticket opened to be closed first. For a Ticket that opened none, every followed Thread must close ({{cite src/core/tickets.ts:95-100}}). The Ticket ends later, once GitHub reports the close ({{cite src/core/tickets.ts:77-89}}).
