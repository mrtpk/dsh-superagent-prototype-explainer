The idea

This tour follows one real path through the system map on the home page: a comment that mentions dsh-superagent's GitHub account. Every stop below names the file and the function the reader is in, with the exact lines.

An everyday comparison. Think of an email that reaches a busy person's inbox. Someone checks whether the sender may ask for this kind of work, and decides to take it on. Only then do they start, reply and eventually close it out. The comparison stops at the gate: dsh-superagent's check is a written rule evaluated in code, not a person's judgment call.

The picture

Read each panel left to right. The three parts match this tour's stops in groups: stops 1-7 build the Ticket, stops 8-11 do the work, and stops 12-13 close it out.

The GitHub {{term source | Source}} reads a comment during a notification or repository poll, and turns it into a {{term trigger | Trigger}}. mentions() matches an @login mention with a word boundary, case-insensitively.

The repository poll calls this from intakeComments(), which reads comments since the Thread's cursor and passes each to ctx.receive() ({{cite src/sources/github.ts:384-402}}).

Intake.receive() normalizes the timestamp, rejects a duplicate id, and checks the Source's scope before the Trigger enters the domain.

Because no Ticket yet subscribes to this comment's {{term thread | Thread}}, the fan-out loop reaches none ({{cite src/core/intake.ts:34-48}}), and the Trigger is queued for {{term eval | Eval}} ({{cite src/core/intake.ts:58}}).

Before Eval batches anything, the active {{term policy | Policy}}'s gate decides the {{term strength | strength}} of every queued Trigger on the Thread. For a human Trigger, an allowed sender who addressed the agent is always explicit.

{{cite src/core/evals.ts:96}} calls this gate once per queued Trigger when Evals.start() runs on the Thread.

Evals.start() takes every Trigger still queued on the Thread, keeps the strongest admissible one, and opens one Eval for the whole batch.

The main Session reads this candidate with orchestrator_eval and orchestrator_eval_read ({{cite src/app/tools/main.ts:202-213}}). An explicit mention from an allowed person skips a full assessment, though, and is routed with orchestrator_route instead ({{cite docs/002-authorization.md:85-87}}).

orchestrator_route lets the main Session decide several candidates in one call. Each item runs as its own Engine command, so one refused item never blocks the others.

Accepting here records a {{term decision | Decision}} and, when it creates one, a Ticket.

{{cite src/app/tools/main.ts:125-153}} defines the tool itself: up to 20 decisions per call, each answered on its own ({{cite src/app/tools/main.ts:129}}).

Evals.decide() routes the accept outcome to accept(), which builds the {{term mandate | Mandate}} the new Ticket will carry.

The Ticket's id is derived from the Eval's own id ({{cite src/core/evals.ts:311}}), so one Eval can never father two Tickets.

Tickets.create() does four things in one call. It builds the Ticket and its first {{term assignment | Assignment}}. It subscribes the Ticket to every Thread of the Eval's Triggers, queues the accept's acknowledgement, and asks the {{term executor | Executor}} to start.

Ticket creation is covered in full on {{link concepts/ticket-lifecycle}}. This tour only follows the one path this mention takes.

Because the comment's Trigger is human and has a {{term channel | Channel}}, the accept's acknowledgement is queued for delivery before the worker even starts.

The {{term outbox | Outbox}} records a receipt and enqueues a durable {{term effect | effect}} in the same transaction ({{cite src/app/outbox.ts:27-32}}). Once dispatched, sendGithub() posts the comment under the agent's account, with a hidden marker so a retry never double-posts it ({{cite src/sources/github-channel.ts:18-45}}).

DshExecutor.start() only enqueues a launch effect; the actual launch runs once a {{term worker-slot | worker slot}} is free.

launch() prepares the Ticket's workspace directory on first use ({{cite src/executor/dsh.ts:434-438}}), then sends the first message with the Ticket's assignment text and the originating Trigger ({{cite src/executor/dsh.ts:449-466}}).

A launch only runs once WorkerSlots.reserve() grants it a slot ({{cite src/executor/dsh.ts:192-194}}). The limit comes from the Executor's maxWorkers setting. A launch for new, proactive work waits in "Queued" until one frees up ({{cite docs/003-execution.md:15}}). A person's own message, or a status request, may use one extra slot beyond that limit. This is why a busy deployment can still answer someone already talking to a Ticket, even while every ordinary slot is full.

The worker reads its assignment and the Ticket's execution variables, which name the agent's GitHub account and the Ticket it is working on.

A pull request the worker opens is recognized as the Ticket's own by its branch name. The branch's last path segment must match the Ticket's short name ({{cite src/sources/github-pull.ts:27-28}}), the same contract {{cite docs/003-execution.md:53}} describes.

orchestrator_report is how a worker tells its Ticket what happened. Naming a pr_number claims that pull request for the Ticket in the same call.

claimPull() accepts only the Ticket's own source PR, or an agent-authored PR on the Ticket's branch, and refuses a PR another open Ticket already claims ({{cite src/sources/github-pull.ts:35-49}}).

Assignments.report() stores the worker's {{term report | report}} on the Assignment, and decides whether this report ends the Ticket.

With an open pull request still followed, this ready report leaves the Ticket in the stage docs/003 calls "Awaiting review" ({{cite docs/003-execution.md:13}}), not ended.

A later poll reads the pull request again. Once it is closed or merged, observePull() reports it to the Ticket that follows it.

Tickets.threadClosed() marks the follow closed and ends the Ticket once it is done with every pull request it follows ({{cite src/core/tickets.ts:77-89}}, {{cite src/core/tickets.ts:345-362}}). GitHub already shows the merge or close on the pull request itself, so the final notice this Ticket would otherwise send skips its GitHub Channels ({{cite src/sources/github-pull.ts:102-104}}).

What can go wrong

Check whether the Ticket still follows an open pull request before reading a ready report as finished work. {{cite src/core/assignments.ts:128-132}} ends the Ticket only once followsDone() has an outcome, which an open, followed pull request does not yet have.
  • An inferred mention would not take this path. This tour assumes an allowed sender's explicit mention. A person not on the allowed list, or a comment that does not mention the agent, takes the admission-table path instead. That path may need auto mode to ever become a Ticket ({{cite docs/002-authorization.md:91-101}}).
  • A later comment on the same Thread does not repeat this tour. Once the Thread's Ticket exists, a later Trigger reaches it through its Subscription, with no new gate check and no new Eval ({{cite src/core/intake.ts:34-48}}).

Why it matters. Reading every comment as a fresh "mention to Ticket" run misses something important. Only the first comment on a Thread takes this full path. Every later one is cheaper, and the worker decides it, not the gate.

Which function decides that an allowed person's mention is explicit, not inferred?

The Policy's gate, {{cite src/policy.ts:191-211}}. Line 197 returns explicit strength once an allowed sender's Trigger is addressed.

 Does the acknowledgement reply wait for the worker to start?

No. {{cite src/core/tickets.ts:49-56}} queues the acknowledgement in the same call that creates the Ticket, before the Executor's launch even reaches a worker slot.

 How does dsh-superagent know a pull request belongs to this Ticket, if the worker opened it itself?

By its branch name. {{cite src/sources/github-pull.ts:27-28}}'s ticketBranch() matches the branch's last path segment against the Ticket's short name, which claimPull() then checks when the worker reports it ({{cite src/sources/github-pull.ts:35-49}}).

 A worker reports ready with an open pull request it is still following. Does the Ticket end?

No. {{cite src/core/assignments.ts:128-132}} only ends the Ticket once followsDone() gives it an outcome, which needs every followed pull request to be closed first ({{cite src/core/tickets.ts:95-100}}). The Ticket ends later, once GitHub reports the close ({{cite src/core/tickets.ts:77-89}}).
