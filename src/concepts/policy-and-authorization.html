The idea

{{term policy | Policy}} is the versioned rule set the Engine reads, plus each Source's own part of it ({{cite src/core/ports.ts:16-27}}, {{cite src/policy.ts:116-118}}). {{term admission | admission}}, the gate, is its first layer: a deterministic check of who may send a Trigger, and with what {{term strength | strength}} ({{cite src/policy.ts:191-211}}). {{term eval | Eval}} then gives the admissible batch to the assessor, and ends with one {{term decision | Decision}} ({{cite src/core/evals.ts:21-26}}). Only an accept Decision grants a {{term mandate | Mandate}}: the strength, scope and Policy version the work relies on ({{cite src/core/model.ts:125-133}}).

An everyday comparison. Think of a building's front desk as the gate: it checks identity against a list before anyone goes further. A supervisor, the assessment, then judges the specific request. Only a signed visitor badge, the Mandate, states its own scope and lets the visit continue. The comparison stops at memory: the gate keeps none of its own. It reads only the Trigger, the Thread, the Tickets subscribed to the Thread, the Policy's settings and the Source's scope ({{cite src/policy.ts:191-211}}, {{cite src/core/part.ts:73-75}}).

In the code

Step 1: the gate judges each queued Trigger

Evals.start() calls policy.gate() once for each pending Trigger on the Thread ({{cite src/core/evals.ts:96}}). It keeps the strongest admissible one. At equal strength, it keeps the latest one ({{cite src/core/evals.ts:95-101}}). For a human Trigger, the gate checks in a fixed order ({{cite src/policy.ts:197-209}}):

  1. An allowed sender who addresses the agent: explicit.
  2. An admission-table cell that says explicit: explicit.
  3. A Thread follow-up: explicit for an allowed sender. For another sender, inferred, but not when the accept mode is off.
  4. An admission-table cell that says inferred: inferred, but not when the accept mode is off.

A non-human Trigger takes a separate path, machineGate(). It admits only listed bots and senderless events that address the agent or that the Source observes, always as inferred. It admits none when the accept mode is off ({{cite src/policy.ts:171-188}}).

Step 2: Eval records a Decision for the gate's result

GateResult is either admissible: false with a reason, or admissible: true with a strength and a basis ({{cite src/core/ports.ts:7}}). Every queued Eval then sends its candidate card to the main Session, for each strength ({{cite src/core/evals.ts:118}}, {{cite src/app/assessment.ts:96-104}}). The main Session assesses an inferred candidate against the rules. It routes an explicit request and does not assess it ({{cite src/app/assessment.ts:39}}, {{cite src/app/assessment.ts:109-113}}). Evals.decide() applies the assessor's outcome to that Eval and records a Decision ({{cite src/core/evals.ts:131-156}}). It refuses to accept an inferred candidate unless Policy.admitsInferred() allows it ({{cite src/core/evals.ts:151-154}}). That needs the accept mode auto, at least one matched rule, and all matched rules still enabled ({{cite src/policy.ts:212}}). assessmentOutcome() itself demotes an inferred accept to an ignored would_accept Decision whenever the accept mode is not auto ({{cite src/policy.ts:55-58}}).

Step 3: an accept decision builds the Mandate

Evals.accept() copies the Eval's strength, actor, Policy version and basis straight into a new Mandate. It adds the matched rules to the basis ({{cite src/core/evals.ts:306-316}}). A Mandate also records scope: what work the accept covers ({{cite src/core/model.ts:126-133}}). It never changes after that, whatever happens to the Ticket it bounds ({{cite src/core/model.ts:125}}).

Step 4: strength, and what the admission table decides

A Mandate's {{term strength | strength}} is explicit or inferred; there is no third, weaker value ({{cite src/core/model.ts:96}}). Not admitted at all is GateResult's admissible: false branch, which carries no strength and grants no Mandate ({{cite src/core/ports.ts:7}}). The admission table itself has three cells per receiving scope. Only the unlistedAddressed cell can say explicit; the other two cells say inferred or ignore ({{cite src/admission.ts:9-10}}). policy.ts's admissionCell() and admissionOf() pick the right cell for a sender and look up its value, or the default ({{cite src/policy.ts:135-140}}, {{cite src/admission.ts:13}}).

More detail

The accept mode, off, observe or auto, is a Policy-wide switch, default observe ({{cite src/policy.ts:84}}). With off, the gate admits nothing inferred ({{cite src/policy.ts:179}}, {{cite src/policy.ts:184}}, {{cite src/policy.ts:206-209}}). Only auto makes an inferred accept real; other modes record it as would_accept ({{cite src/policy.ts:55-58}}). The Policy version is a hash of the rules, the accept mode and each Source's part ({{cite src/policy.ts:116-118}}). Every Mandate and Decision records it ({{cite src/core/model.ts:128}}, {{cite src/core/model.ts:197}}). A version change does not revoke a live Mandate by itself. policyEffects() only computes what changed, and the Ticket gets it as an Input that its Executor reads ({{cite src/policy.ts:144-165}}, {{cite src/core/tickets.ts:200-208}}). Eval's own timeout is a separate setting: eval.timeoutSeconds, default 120, becomes evalTimeoutMs ({{cite src/policy.ts:85}}, {{cite src/policy.ts:190}}). The deadline counts again from when the candidate reaches the assessor ({{cite src/core/evals.ts:48-54}}).

Mandate's basis.viaWhat revalidate() checks
addressedHolds while the sender stays on the Source's allowed list ({{cite src/policy.ts:236}}).
an explicit followupAlways holds ({{cite src/policy.ts:221}}).
an inferred followupHolds only in auto mode, with its matched rules still enabled ({{cite src/policy.ts:221}}).
botHolds only while the bot stays on the Source's bot list. A bot Mandate is always inferred, so it also needs auto mode and its matched rules still enabled ({{cite src/policy.ts:223}}, {{cite src/policy.ts:238}}).
admissionHolds only while the sender's current cell still grants at least the original strength ({{cite src/policy.ts:225-235}}). An inferred one also needs auto mode and its matched rules still enabled ({{cite src/policy.ts:238}}).

Every basis also fails at once if the Source no longer listens to the scope where it received the Trigger ({{cite src/policy.ts:217-218}}).

For the full authorization model, including bots, automated reviewers and revalidation after a processing pause, see the repository's own {{cite docs/002-authorization.md}}.

What can go wrong

A weaker rule or admission cell does not stop an open Ticket. The Ticket only gets a policy-changed Input ({{cite src/core/tickets.ts:200-208}}). The current Policy checks the Mandate again only before an ended Ticket resumes or takes an attached message ({{cite src/core/tickets.ts:113}}, {{cite src/core/tickets.ts:257}}).
  • An inferred accept is refused outside auto mode, even if the assessment itself says accept. Evals.decide() throws a notExplicit error and records no Decision, unless Policy.admitsInferred() allows the matched rules ({{cite src/core/evals.ts:151-154}}).
  • Explicit admission always wins over a Thread follow-up, never the reverse. The gate checks an explicit admission-table cell before the follow-up case. Thus a Thread's existing Tickets cannot change an explicit request into an inferred follow-up ({{cite src/policy.ts:203-206}}).

This page's basis table leaves out via: 'listed', which the code's own comment says is for a Mandate accepted before Mandates recorded their basis ({{cite src/core/model.ts:112-113}}). Only the settings migration makes this basis ({{cite src/app/migration.ts:359}}).

Why it matters. If a person thinks that a Policy change acts immediately, the person can make two mistakes. The person can think that a Ticket lost authority that it still has. Or the person can trust a Ticket that a resume would refuse.

What does an accept Decision grant that nothing else does?

A Mandate: the strength, scope and Policy version the work relies on ({{cite src/core/model.ts:125-133}}). Only Evals.accept() builds one ({{cite src/core/evals.ts:306-316}}).

 What are the two Strength values a Mandate can record?

explicit and inferred ({{cite src/core/model.ts:96}}). Not admitted at all is GateResult's admissible: false branch, which carries no strength ({{cite src/core/ports.ts:7}}).

 In what order does the gate check a human Trigger?

An allowed sender who addresses the agent first, then an explicit admission-table cell, then a Thread follow-up, then an inferred admission-table cell ({{cite src/policy.ts:197-209}}). The explicit cell comes before the follow-up case, so a Thread's own Tickets cannot weaken an explicit request to a follow-up ({{cite src/policy.ts:203-204}}).

 Why can switching the accept mode from auto to observe not immediately end an open Ticket's authority?

A Policy change does not stop a live Ticket. A failed revalidation refuses only an ended Ticket that would resume or take an attached message ({{cite src/core/tickets.ts:113}}, {{cite src/core/tickets.ts:257}}). For an inferred Mandate, the mode change makes policyEffects() compute a proactive: false effect ({{cite src/policy.ts:155-160}}). The Ticket gets it as an Input that its Executor reads ({{cite src/core/tickets.ts:206}}). The Mandate itself does not change.
