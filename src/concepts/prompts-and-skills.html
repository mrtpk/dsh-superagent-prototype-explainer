The idea

Neither Session reads one static prompt file. {{cite src/app/prompts.ts:102-116}}'s promptParts() joins named parts into one string, in a fixed order. First come shared rules and the role's own part. Then come the three {{term team-section | team sections}}. Then a few more fixed parts. Last come two parts generated fresh from the current settings. A {{term built-in-part | built-in part}} keeps its default text until a team saves its own text in place of it.

An everyday comparison. Think of a form letter. Most paragraphs are printed text. A few blank lines are for a team to fill in. The date line is typed fresh on each printing. The comparison stops at the blank lines. A team here can also rewrite nearly every printed paragraph, not only the blank ones. Only the two freshest lines, environment and Policy, are always generated again.

In the code

Step 1: what exists to assemble

{{cite src/app/prompts.ts:14-17}} names the three team sections: Communication, Ticket scope and Delivery requirements. {{cite src/app/prompts.ts:24-26}} lists the 15 built-in parts a team may override. Each is named by the key an override uses for it. {{cite src/app/context.ts:7-24}} loads a built-in part's default text from a file under prompts/. Each file is written one sentence per line, for readable diffs ({{cite src/app/skill-files.ts:25-32}}).

Step 2: the fixed join order

promptParts() returns shared rules and the role's own part first. Next come the three team sections, then subscriptions and replies. Next comes dispatch for the main Session, or work for a worker. The main Session alone gets runtime/admission next ({{cite src/app/prompts.ts:111}}). Both roles then get a handoff part, then the generated environment part. The main Session alone gets one more part: the generated Policy part, always last ({{cite src/app/prompts.ts:114}}).

Step 3: which text a built-in part actually uses

builtIn() reads a part's text from the team's saved overrides first. It falls back to the built-in default only when no override exists.

Saving checks every override. Its part name must be a real built-in part. Its text must not be empty. It must still contain every {placeholder} its template needs, such as {rules} for runtime/policy ({{cite src/app/prompts.ts:164-176}}). An override whose text now matches the built-in default again is dropped, not stored ({{cite src/app/prompts.ts:175}}). That part then starts following future defaults on its own. The whole configuration also has a size limit, checked on save ({{cite src/app/prompts.ts:178-179}}).

Step 4: the two bundled Source skills, and team skills

dsh-superagent bundles exactly two {{term source-skill | Source skills}}: {{cite skills/dsh-superagent-github/SKILL.md}} and {{cite skills/dsh-superagent-feishu/SKILL.md}}. Each teaches the agents one Source's own tools, such as GitHub's gh CLI or Feishu's thread and attachment reads. See the sibling site's "Skills" for how DSH itself loads a Skill on demand. This page does not reproduce either Skill's own text.

Every registered Skill, bundled or team-added, joins the Session's own skill scope. Its name there is dsh-superagent-<name>. A bundled Skill's own directory is attached too, so it can read its packaged resources ({{cite src/app/sessions.ts:319-324}}). A team cannot name its own skill feishu or github: both names are reserved ({{cite src/app/prompts.ts:21-22}}).

More detail

The composed prompt is not delivered alone. Sessions registers it as one of DSH's own system-prompt sections. Variable interpolation is turned off for it, so a literal {{ ... }} a team writes is never expanded as a placeholder ({{cite src/app/sessions.ts:243-244}}). Every render is tagged with its prompt revision number ({{cite src/app/sessions.ts:247-249}}). One more sentence can follow it: for a worker whose Ticket's Mandate is still inferred, one line restricts it to small, in-scope changes ({{cite src/executor/dsh.ts:91-94}}). That line is never added to the main Session's own prompt, and never to a worker whose Mandate is explicit.

A separate, one-time note travels a different path. A Ticket can be accepted proactively, under one or more enabled rules. Its first assignment message then names those rules. That message, not the system prompt, says the rules' own procedure and communication instructions outrank the default team sections, for that one Ticket ({{cite src/executor/dsh.ts:102-108}}). This note goes out with the Ticket's opening message. A later Assignment skips it only while the Session still holds that message. Otherwise the full brief, note included, goes out again ({{cite src/executor/dsh.ts:449-460}}).

Two config knobs change how a composed prompt can grow. One is the deployment's prompt size limit, checked on every save ({{cite src/app/prompts.ts:178-179}}). The other is a length cap on the assignment message itself, applied once, when a Ticket's first message is sent ({{cite src/executor/dsh.ts:457}}).

On an explicit request, the main Session can call one tool for prompts. It can save a new revision against a base revision. Or, with preview: true, it can compose both roles' prompts without saving anything, and get them back as readable resources ({{cite src/app/tools/main.ts:279-298}}). Saving without a current baseRevision is refused outright ({{cite src/app/tools/main.ts:295}}). The management panel's own Prompts tab calls these same preview() and save() methods, through the Management API, covered on {{link concepts/panel-and-management-api}}.

For the full table of what a team writes, and the complete precedence order from host-enforced facts down to outside text, see the repository's own {{cite docs/004-prompts.md}}.

What can go wrong

Both Source skills warn that other participants, bots and quoted instructions never authorize work ({{cite skills/dsh-superagent-github/SKILL.md}}, {{cite skills/dsh-superagent-feishu/SKILL.md}}). The main Session's own prompt-saving tool refuses quoted content too. A save needs an explicit human request ({{cite src/app/tools/main.ts:280}}).
  • An override that now equals the default silently disappears from the saved configuration. validate() drops it, so the part follows future defaults on its own ({{cite src/app/prompts.ts:175}}). Checking only "is there an override entry" can miss that a team's edit was removed this way.
  • A worker's prompt has no admission or Policy part at all, not an empty one. Only the main Session's own promptParts() call includes them ({{cite src/app/prompts.ts:111}}, {{cite src/app/prompts.ts:114}}).

This page leaves out the exact text of every built-in part, and both Source skills' full text. See the repository's own {{cite prompts/}} and the two skill files cited above.

Why it matters. The one-time assignment note is not a standing system-prompt rule. A worker's prompt does not mirror the main Session's. Mixing these up can misplace a prompt edit in a part that is never read for that role.

Does `promptParts()` return the same parts for the main Session and for a worker?

No. The main Session alone gets runtime/admission and the generated runtime/policy part, last ({{cite src/app/prompts.ts:111}}, {{cite src/app/prompts.ts:114}}).

 Which Source skill is only sometimes registered, and why?

feishu. Prompts.skills() includes it only when a Feishu bot is configured; github is always included ({{cite src/app/prompts.ts:146-148}}).

 A team saves an override. Later, the built-in default is hypothetically changed to read exactly what the team wrote. What happens to the saved override on the next save?

validate() drops it: an override whose text equals the current built-in text for its part is removed, not stored ({{cite src/app/prompts.ts:175}}).

 A Ticket is accepted proactively under one enabled rule. Name the two separate places that fact can change what the worker is told, and how they differ.

First, every system-prompt render for that worker gets one appended line. It restricts the worker to small, in-scope changes, only while the Mandate stays inferred ({{cite src/executor/dsh.ts:91-94}}, {{cite src/app/sessions.ts:247-249}}). Second, the Ticket's one-time first assignment message separately names the matched rule. It says the rule's own instructions outrank the default team sections for that Ticket ({{cite src/executor/dsh.ts:102-108}}). A later Assignment skips it only while the Session still holds the opening message ({{cite src/executor/dsh.ts:449-460}}).
