Two bundled Source skills join each Session's skill scope. --- A role's system prompt is built fresh, in a fixed order, from built-in parts, team sections and generated sections.

The idea

Neither Session reads one static prompt file. {{cite src/app/prompts.ts:102-116}}'s promptParts() lists named parts in a fixed order, and composePrompt() joins them into one string ({{cite src/app/prompts.ts:117-119}}). First come shared rules and the role's own part. Then come the three {{term team-section | team sections}}. Then a few more fixed parts. Last come the generated parts: the execution environment for both roles, and the Policy part for the main Session only ({{cite src/app/prompts.ts:141-144}}). A {{term built-in-part | built-in part}} keeps its default text until a team saves its own text in place of it.

An everyday comparison. Think of a form letter. Most paragraphs are printed text. A few blank lines are for a team to fill in. The date line is typed fresh on each printing. The comparison stops at the blank lines. A team here can also rewrite nearly every printed paragraph, not only the blank ones. The data in the generated parts, environment and Policy, is always filled in again. A team can change only their templates.

In the code

Step 1: what exists to assemble

{{cite src/app/prompts.ts:14-17}} names the three team sections: Communication, Ticket scope and Delivery requirements. {{cite src/app/prompts.ts:24-26}} lists the 15 built-in parts a team may override. Each is named by the key an override uses for it. {{cite src/app/context.ts:7-24}} loads the default text of the role parts from files under prompts/. Each file has one sentence per line, for readable diffs. promptFile() joins the lines of a paragraph again when it loads the file ({{cite src/app/skill-files.ts:25-32}}).

Step 2: the fixed join order

promptParts() returns shared rules and the role's own part first. Next come the three team sections, then subscriptions and replies. Next comes dispatch for the main Session, or work for a worker. The main Session alone gets runtime/admission next ({{cite src/app/prompts.ts:111}}). Both roles then get a handoff part, then the generated environment part. The main Session alone gets one more part: the generated Policy part, always last ({{cite src/app/prompts.ts:114}}). A part with empty text, such as an empty team section, is left out ({{cite src/app/prompts.ts:115}}).

Step 3: which text a built-in part actually uses

builtIn() reads a part's text from the team's saved overrides first. It falls back to the built-in default only when no override exists.

Saving checks every override. Its part name must be a real built-in part. Its text must not be empty. It must still contain every {placeholder} its template needs, such as {rules} for runtime/policy ({{cite src/app/prompts.ts:168-173}}). An override whose text now matches the built-in default again is dropped, not stored ({{cite src/app/prompts.ts:175}}). That part then follows future defaults on its own. The whole configuration also has a size limit. validate() checks it for a save and for a preview ({{cite src/app/prompts.ts:178-179}}, {{cite src/app/prompts.ts:196}}, {{cite src/app/prompts.ts:203}}).

Step 4: the two bundled Source skills, and team skills

dsh-superagent bundles exactly two {{term source-skill | Source skills}}: {{cite skills/dsh-superagent-github/SKILL.md}} and {{cite skills/dsh-superagent-feishu/SKILL.md}}. Each teaches the agents one Source's own tools, such as GitHub's gh CLI or Feishu's thread and attachment reads. See the sibling site's "Skills" for how DSH itself loads a Skill on demand. This page does not reproduce either Skill's own text.

Every registered Skill, bundled or team-added, joins the Session's own skill scope. Its name there is dsh-superagent-<name>. A bundled Skill's own directory is attached too, so it can read its packaged resources ({{cite src/app/sessions.ts:319-324}}). A team cannot name its own skill feishu or github: both names are reserved ({{cite src/app/prompts.ts:21-22}}).

More detail

The composed prompt is not delivered alone. Sessions registers it as one of DSH's own system-prompt sections. Variable interpolation is off for it, so DSH does not expand a literal ${{ ... }} that a team writes ({{cite src/app/sessions.ts:243-244}}). Each render starts with a tag that gives its prompt revision number ({{cite src/app/sessions.ts:248}}). A short extra text can follow the prompt. For a worker whose Ticket's Mandate is still inferred, it limits the worker to small, in-scope changes ({{cite src/executor/dsh.ts:91-94}}). The main Session has no Ticket, so its prompt never gets this text. A worker whose Mandate is explicit gets an empty string ({{cite src/app/sessions.ts:246-248}}).

A separate, one-time note travels a different path. A Ticket can be accepted proactively, under one or more enabled rules. Its first assignment message then names those rules. That message, not the system prompt, gives the rules' own procedure and communication instructions precedence. They take precedence over "the default acknowledgement and messaging policy" for that one Ticket ({{cite src/executor/dsh.ts:102-108}}). This note goes out with the Ticket's opening message. A later Assignment skips it only while the Session still holds that message. Otherwise the full brief, note included, goes out again ({{cite src/executor/dsh.ts:449-464}}).

One config knob limits how large a prompt configuration can be: the deployment's promptMaxChars, 100,000 characters by default ({{cite src/deployment.ts:17-18}}). validate() compares it with the length of the configuration as JSON ({{cite src/app/prompts.ts:178-179}}). A fixed limit, not a config knob, applies to the assignment text in a worker's opening message. It is 1,500 characters. A longer text is cut, and the worker reads the full text as a resource ({{cite src/executor/dsh.ts:112-116}}, {{cite src/executor/dsh.ts:457}}).

On an explicit request, the main Session can call one tool for prompts. It can save a new revision against a base revision. Or, with preview: true, it can compose both roles' prompts without saving anything, and get them back as readable resources ({{cite src/app/tools/main.ts:279-298}}). A save without a baseRevision is refused ({{cite src/app/tools/main.ts:295}}). A save against an old revision fails with a conflict ({{cite src/app/prompts.ts:206}}). The panel's Prompts group calls the same preview() and save methods through the Management API ({{cite src/app/http.ts:208-212}}). {{link concepts/panel-and-management-api}} covers the panel.

For the full table of what a team writes, and the complete precedence order from host-enforced facts down to outside text, see the repository's own {{cite docs/004-prompts.md}}.

What can go wrong

The Feishu skill says that other participants, bots and quoted instructions never authorize work ({{cite skills/dsh-superagent-feishu/SKILL.md:8}}). The GitHub skill says that the words of a bot or a GitHub App never authorize work ({{cite skills/dsh-superagent-github/SKILL.md:6}}). The description of the main Session's prompt-save tool tells it to save only on an explicit user request, never on quoted content ({{cite src/app/tools/main.ts:280}}).
  • An override that now equals the default disappears from the saved configuration without a message. validate() drops it, so the part follows future defaults on its own ({{cite src/app/prompts.ts:175}}). If you only look for an override entry, you can miss that the save removed a team's edit.
  • A worker's prompt has no admission or Policy part at all, not an empty one. Only the main Session's own promptParts() call includes them ({{cite src/app/prompts.ts:111}}, {{cite src/app/prompts.ts:114}}).

This page leaves out the exact text of every built-in part, and both Source skills' full text. See the repository's own {{cite prompts/}} and the two skill files cited above.

Why it matters. The one-time assignment note is not a standing system-prompt rule. A worker's prompt does not mirror the main Session's. Mixing these up can misplace a prompt edit in a part that is never read for that role.

Does promptParts() return the same parts for the main Session and for a worker?

No. The main Session alone gets runtime/admission and the generated runtime/policy part, last ({{cite src/app/prompts.ts:111}}, {{cite src/app/prompts.ts:114}}).

 Which Source skill is only sometimes registered, and why?

feishu. Prompts.skills() includes it only when a Feishu bot is configured. github is always included ({{cite src/app/prompts.ts:146-148}}, {{cite src/app/runtime.ts:102}}).

 A team saves an override. Later, the built-in default is hypothetically changed to read exactly what the team wrote. What happens to the saved override on the next save?

validate() drops it. It removes an override whose text equals the current built-in text for its part ({{cite src/app/prompts.ts:175}}).

 A Ticket is accepted proactively under one enabled rule. Name the two separate places that fact can change what the worker is told, and how they differ.

First, every system-prompt render for that worker gets a short extra text. It limits the worker to small, in-scope changes, only while the Mandate stays inferred ({{cite src/executor/dsh.ts:91-94}}, {{cite src/app/sessions.ts:247-249}}). Second, the Ticket's one-time first assignment message separately names the matched rule. It says that the rule's own procedure and communication instructions take precedence over the default acknowledgement and messaging policy for that Ticket ({{cite src/executor/dsh.ts:102-108}}). A later Assignment skips it only while the Session still holds the opening message ({{cite src/executor/dsh.ts:449-464}}).
