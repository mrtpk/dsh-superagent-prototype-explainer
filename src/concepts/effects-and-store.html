Store is the one SQLite file behind it, where each kind of state has exactly one writer. --- A command enqueues an {{term effect | Effect}} inside its own transaction in the {{term store | Store}}, and it runs only after that transaction commits.

The idea

Every {{term effect | Effect}} is a row in the Store's effect table before it is a promise in memory ({{cite src/app/effects.ts:42-45}}). A command enqueues it inside its own transaction ({{cite src/app/effects.ts:60-61}}). enqueue() only schedules a dispatch for later, as a microtask ({{cite src/app/effects.ts:84-88}}). atomic() runs the whole transaction synchronously, so a handler can run the row only after the transaction commits ({{cite src/app/store.ts:140-152}}). {{term store | Store}} is the one SQLite database behind every Trigger, Thread, Ticket and Decision, the effect queue itself, and the {{term outbox | Outbox}}'s receipts ({{cite src/app/store.ts:46-50}}, {{cite src/app/store.ts:72-82}}).

An everyday comparison. Think of a restaurant's order slip: the kitchen only starts cooking once the till has printed and saved the order, never before. The comparison stops at retries. A kitchen does not try a slip again with a longer delay after each failure, but the effect queue does this for a failed Effect ({{cite src/app/effects.ts:140-144}}).

In the code

Step 1: enqueue writes a row; a handler reads it back after commit

enqueue() upserts one row keyed by its kind and key, inside the transaction that the caller already has open ({{cite src/app/effects.ts:60-66}}). The effect table's primary key is (kind, key) ({{cite src/app/store.ts:80-82}}). So a second enqueue of the same waiting key replaces its payload, resets its failure count and makes it due now. Its place in the queue (seq) does not change ({{cite src/app/effects.ts:62-63}}).

Step 2: each of the six kinds has exactly one handler

handle() throws if a kind already has a handler ({{cite src/app/effects.ts:67-68}}). assessment, launch, delivery, relay, notice and reply are the six kinds ({{cite src/app/effects.ts:11-24}}). MasterAssessor runs assessment; {{link concepts/executor-and-worker-sessions | DshExecutor}} runs launch and delivery; Sessions runs relay and notice; and Outbox runs reply ({{cite src/app/assessment.ts:96}}, {{cite src/executor/dsh.ts:232-235}}, {{cite src/app/sessions.ts:104-105}}, {{cite src/app/outbox.ts:24}}).

Step 3: Engine and Outbox are each the sole writer of their own state

The Engine is the only part of the code that changes a Trigger, a Thread, a Decision, a Ticket or an Assignment ({{cite src/core/engine.ts:19-20}}). The Outbox is the only writer of its own receipts ({{cite src/app/store.ts:253}}).

More detail

atomic() nests savepoints: a failure rolls back only its own level. Post-commit callbacks queued inside it wait for the outermost transaction to commit before any of them run ({{cite src/app/store.ts:136-152}}). afterCommit() is for an in-memory follow-up that need not survive a restart, such as the cancel of a turn. A side effect that must survive a crash goes through Effects instead ({{cite src/app/store.ts:154-158}}). An effect kind's health entry shows an error when one of its rows failed three times in a row. The exception is delivery, whose failures show on the Ticket itself instead ({{cite src/app/effects.ts:6-7}}, {{cite src/app/effects.ts:155}}, {{cite src/executor/dsh.ts:234-235}}).

Rows waiting in the effect table survive a restart. drain() starts no new rows and waits only for the rows that already run. The other rows stay in SQLite for the next start ({{cite src/app/effects.ts:98-102}}). A row that fails during the shutdown also stays as it is ({{cite src/app/effects.ts:136-137}}). An afterCommit() callback is never written to SQLite, so a crash before it runs loses it for good. Runtime locks the state directory before it opens Store, so a second process cannot migrate or write the same database at the same time ({{cite src/app/runtime.ts:90-93}}).

For the full list of effect kinds with their retry delays, and the Store's own read queries, see the repository's own {{cite docs/007-architecture.md:149-181}}.

What can go wrong

The delivery handler is registered with quiet: true. Three failed attempts in a row do not mark it as an error on the effect queue's health board ({{cite src/app/effects.ts:155}}). The failure shows on the Ticket itself instead ({{cite src/executor/dsh.ts:234-235}}, {{cite src/executor/dsh.ts:322}}).
  • afterCommit() is not durable. A callback queued with it runs once, in memory. A crash before it runs loses it. Only a row enqueued through Effects survives a crash ({{cite src/app/store.ts:154-158}}).

This page covers only the domain aggregates and the outbox receipts. Settings and the key-value store have their own writers too. See the repository's own {{cite docs/007-architecture.md:153-160}} for the full list of Store's interfaces.

Why it matters. Treating every stored row as equally durable can hide a real gap. An in-memory follow-up queued with afterCommit() does not come back after a crash, while a queued Effect does.

What makes an Effect durable, and not only a promise in memory?

It is a row in the Store's effect table, written inside the caller's own transaction, before any handler runs it ({{cite src/app/effects.ts:42-45}}, {{cite src/app/effects.ts:60-66}}).

 How many handlers can one effect kind have at a time?

Exactly one. handle() throws if a kind already has a registered handler ({{cite src/app/effects.ts:67-68}}).

 Which part of the code is the only one allowed to change a Ticket's Assignments?

The Engine. It is the single writer of Triggers, Threads, Decisions, Tickets and Assignments ({{cite src/core/engine.ts:19-20}}).

 The host crashes mid-turn. Which survives for the next start: a queued launch Effect, or an action scheduled with afterCommit()?

The queued Effect. It is a row in SQLite, and the next start finds it there ({{cite src/app/effects.ts:42-45}}, {{cite src/app/effects.ts:98-102}}). An afterCommit() callback exists only in memory and is lost with the crash ({{cite src/app/store.ts:154-158}}).
