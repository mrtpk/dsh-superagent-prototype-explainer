--- title: The Executor and worker Sessions: one Session per Ticket, a concurrency limit nav_title: The Executor and worker sessions level: Intermediate prerequisites: concepts/ticket-lifecycle related: concepts/effects-and-store, concepts/policy-and-authorization, tours/life-of-a-github-mention summary: DshExecutor gives every accepted Ticket one worker Session and one directory. WorkerSlots caps how many may run at once, with one slot kept for a person's message. --- The {{term executor | Executor}} gives every accepted {{term ticket | Ticket}} one worker Session and one directory, and a {{term worker-slot | worker slot}} caps how many may run at once.

The idea

{{term executor | Executor}} is the port the Engine calls to run a Ticket's work ({{cite src/core/ports.ts:59-69}}). It has three methods. start() queues a pending {{term assignment | Assignment}} for launch. deliver() queues the delivery of waiting Inputs to a running one. stop() ends an Assignment's work after the domain has already ended it. DshExecutor is the only Executor in src/, and Runtime makes it ({{cite src/executor/dsh.ts:207}}, {{cite src/app/runtime.ts:128}}). It gives each accepted Ticket one Session, named worker-<ticket id>, and one directory under the configured execution root ({{cite src/executor/dsh.ts:23-24}}, {{cite src/executor/dsh.ts:110}}).

An everyday comparison. Think of the Executor as a dispatcher who gives each job its own worker and its own workbench, never two jobs on one bench. The comparison stops at capacity. A dispatcher with a full floor turns new jobs away, but dsh-superagent only makes a new launch wait. It also keeps one extra slot, so that a person's message to an existing worker does not wait behind new launches.

A worker Session uses the same turn/step/round vocabulary as any DSH Session. See the sibling site's "Turn, step, round: the session vocabulary". What dsh-superagent adds on top is one dedicated worker Session per Ticket, and a limit on how many may run together.

In the code

Step 1: the Executor port only queues the work

start() and deliver() do not launch or deliver anything at once. Each enqueues an {{term effect | Effect}} and returns ({{cite src/executor/dsh.ts:264-268}}). {{link concepts/effects-and-store}} covers Effects in full. DshExecutor's own launch and delivery handlers do the work later ({{cite src/executor/dsh.ts:232-235}}).

Step 2: WorkerSlots reserves a slot before anything starts

WorkerSlots tracks which Tickets currently hold a slot, and the configured maximum ({{cite src/executor/dsh.ts:171-180}}). reserve() adds a Ticket before a launch or a wake starts. It throws Later when no slot is free, and the effect queue tries again later ({{cite src/executor/dsh.ts:192-196}}, {{cite src/app/effects.ts:138-139}}).

A new launch always reserves with by: 'launch', never 'person' ({{cite src/executor/dsh.ts:274}}). Only a wake of an idle worker, for an Input from a person, gets the extra slot ({{cite src/executor/dsh.ts:305-310}}). That wake can start when all normal slots are full, so it does not wait behind new launches ({{cite src/executor/dsh.ts:166-169}}). executor.maxWorkers defaults to 3 and can be set from 1 to 16 ({{cite src/policy.ts:93}}, {{cite src/limits.ts:6}}).

Step 3: a Ticket keeps its slot through background work

A Ticket's worker holds its slot while its turn runs. It also holds the slot while a shell job or a subagent it started keeps running after the turn ends ({{cite src/executor/dsh.ts:405-409}}). Shell jobs and subagents are DSH's own background-work mechanism; see the sibling site's "Jobs, workflows, goals and plan mode". Subagents are on a separate sibling page, "Subagents and delegation". What dsh-superagent adds is a 30-minute limit ({{cite src/executor/dsh.ts:31-32}}). After that limit, the Executor kills the worker's shell jobs, and the worker gets a note about them at its next turn. Subagents continue ({{cite src/executor/dsh.ts:643-656}}). The Executor also records a waiting Report, unless the worker already handed off to a person ({{cite src/executor/dsh.ts:658}}, {{cite src/executor/dsh.ts:663-665}}).

A handoff to a person frees the slot at once. A handoff is a ready Report, a question for a person, or a blocked or failed Report, with no later Input ({{cite src/executor/dsh.ts:612-628}}). Subagents stop. A shell job, such as a server started for review, continues for the person and holds no slot ({{cite src/executor/dsh.ts:583-600}}).

More detail

The launch effect's own concurrency limit already excludes the slots that a wake uses ({{cite src/executor/dsh.ts:182-185}}). Then reserve() claims the slot when the launch starts ({{cite src/executor/dsh.ts:232-233}}, {{cite src/executor/dsh.ts:274}}). One config knob changes how many Tickets run at once: executor.maxWorkers. WorkerSlots reads it again each time it checks its limit ({{cite src/executor/dsh.ts:229-230}}). A larger value lets more launches run together. The extra slot for a person's message stays exactly one above the limit ({{cite src/executor/dsh.ts:194}}).

A turn ends when nothing runs for it in the background: no shell job, no subagent, and the Session itself is idle ({{cite src/executor/background.ts:89-96}}, {{cite src/executor/dsh.ts:642}}). A transient model-provider or network failure does not end an Assignment. The Executor tells the worker to continue, up to three times ({{cite src/executor/dsh.ts:548-553}}, {{cite src/executor/dsh.ts:509}}). The wait is 15, 30, then 60 seconds ({{cite src/executor/dsh.ts:30}}, {{cite src/executor/dsh.ts:575}}). A fourth such failure records a failed Report ({{cite src/executor/dsh.ts:510}}). A host restart is different. At the next start, the Executor cancels a running Assignment's turn and stops its shell jobs and subagents. Then it tells the Engine. The Engine restarts the Assignment with a recovery note. It skips the restart, and keeps the Session, only under two conditions. First, the last Report must already be waiting, ready, blocked or failed. Second, no later Input reached the worker after that Report ({{cite src/executor/dsh.ts:524-536}}, {{cite src/core/engine.ts:240-247}}, {{cite src/core/assignments.ts:83-90}}).

For the exact stage table, the retry and restart rules, and every execution variable a worker reads, see the repository's own {{cite docs/003-execution.md}}.

What can go wrong

A brand-new Ticket's first launch always reserves with by: 'launch'. It can wait behind a full set of normal slots even when a person is involved. Only a wake of an idle worker for that person's own message gets the extra slot ({{cite src/executor/dsh.ts:192-194}}, {{cite src/executor/dsh.ts:274}}).
  • A Ticket whose turn ended may still hold a slot. Background jobs and subagents keep a worker's slot for up to 30 minutes after its turn ends. If you count only the Tickets whose turn runs, you see more free slots than there are ({{cite src/executor/dsh.ts:31-32}}, {{cite src/executor/dsh.ts:405-409}}).

This page leaves out the retry schedule of a failed launch and the 10-minute timeout of the workspace prepare command ({{cite src/executor/dsh.ts:28}}). See the repository's own {{cite docs/003-execution.md}} for both.

Why it matters. Reading "3 of 3 slots used" as "3 Tickets are actively working" can be wrong. One of them may only be waiting on a background job after its own turn already ended.

What two things does the Executor give every accepted Ticket?

One Session, named worker-<ticket id>, and one directory under the execution root ({{cite src/executor/dsh.ts:23-24}}, {{cite src/executor/dsh.ts:110}}).

 Name the three methods the Engine calls on an Executor.

start(), deliver() and stop() ({{cite src/core/ports.ts:59-69}}).

 Can a Ticket's very first launch use the one extra worker slot kept for a person's message?

No. A launch always reserves with by: 'launch'. Only a wake of an idle worker for an Input from a person may use the extra slot ({{cite src/executor/dsh.ts:192-194}}, {{cite src/executor/dsh.ts:274}}).

 A worker's turn fails because of a provider timeout. Does its Assignment fail right away?

No. A timeout is a transient failure ({{cite src/executor/dsh.ts:44-54}}). The Executor tells the worker to continue, up to three times ({{cite src/executor/dsh.ts:548-553}}). The wait starts at 15 seconds and doubles each time ({{cite src/executor/dsh.ts:30}}, {{cite src/executor/dsh.ts:575}}). Only a fourth failure records failed ({{cite src/executor/dsh.ts:509-510}}).
