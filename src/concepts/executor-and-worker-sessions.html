WorkerSlots caps how many may run at once, with one slot kept for a person's message. --- The {{term executor | Executor}} gives every accepted {{term ticket | Ticket}} one worker Session and one directory, and a {{term worker-slot | worker slot}} caps how many may run at once.

The idea

{{term executor | Executor}} is the port the Engine calls to run a Ticket's work ({{cite src/core/ports.ts:59-69}}). It has three methods: start() launches a pending {{term assignment | Assignment}}, deliver() steers waiting Inputs to a running one, and stop() ends one. DshExecutor is the only Executor this repository registers ({{cite src/executor/dsh.ts:207}}). It gives each accepted Ticket one Session, named worker-<ticket id>, and one directory under the configured execution root ({{cite src/executor/dsh.ts:23-24}}).

An everyday comparison. Think of the Executor as a dispatcher who gives each job its own worker and its own workbench, never two jobs on one bench. The comparison stops at capacity. A dispatcher with a full floor turns new jobs away, but dsh-superagent only makes a new launch wait. It never turns away a person already talking to an existing worker.

A worker Session follows the same turn/step/round vocabulary as any DSH Session; see the sibling site's "Turn, step, round: the session vocabulary". What dsh-superagent adds on top is one dedicated worker Session per Ticket, and a limit on how many may run together.

In the code

Step 1: the Executor port only queues the work

DshExecutor does not launch or deliver anything itself. start() and deliver() each enqueue an {{term effect | Effect}}, covered in full on {{link concepts/effects-and-store}}, and return at once ({{cite src/executor/dsh.ts:264-268}}).

Step 2: WorkerSlots reserves a slot before anything starts

WorkerSlots tracks which Tickets currently hold a slot, and the configured maximum ({{cite src/executor/dsh.ts:171-180}}). reserve() adds a Ticket before a launch or a wake starts, and throws when none is free.

A new launch always reserves with by: 'launch', never 'person' ({{cite src/executor/dsh.ts:274}}). Only a wake of an idle worker for a person's own message gets the extra slot. It then takes the next free slot ahead of a new launch ({{cite src/executor/dsh.ts:305-310}}). executor.maxWorkers defaults to 3 and can be set from 1 to 16 ({{cite src/policy.ts:93}}, {{cite src/limits.ts:6}}).

Step 3: a Ticket keeps its slot through background work

A Ticket's worker holds its slot while its turn runs. It also holds the slot while a shell job or a subagent it started keeps running after the turn ends ({{cite src/executor/dsh.ts:405-409}}). Shell jobs and subagents are DSH's own background-work mechanism; see the sibling site's "Jobs, workflows, goals and plan mode". What dsh-superagent adds is a 30-minute limit: past it, a worker's shell jobs are killed and it reports waiting at its next turn ({{cite src/executor/dsh.ts:31-32}}, {{cite src/executor/dsh.ts:643-656}}).

A handoff to a person, after a ready Report, a question, or a blocked or failed Report, frees the slot at once. Subagents stop, and any shell job, such as a server started for review, keeps running for the person without holding a slot ({{cite src/executor/dsh.ts:583-600}}).

More detail

The launch effect's own concurrency limit already excludes slots a wake is using ({{cite src/executor/dsh.ts:182-185}}), before reserve() claims the slot itself when the launch actually starts ({{cite src/executor/dsh.ts:232-233}}). One config knob changes how many Tickets run at once: executor.maxWorkers, read fresh every time WorkerSlots checks its limit ({{cite src/executor/dsh.ts:229-230}}). Raising it lets more launches run together. It never changes the one extra slot kept for a person's message: that stays exactly one beyond the limit ({{cite src/executor/dsh.ts:194}}).

A turn ends once nothing runs for it in the background: no shell job, no subagent, and the Session itself is idle ({{cite src/executor/background.ts:89-96}}). A transient model-provider or network failure does not end an Assignment. The worker is told to go on, up to three tries ({{cite src/executor/dsh.ts:548-553}}), with a backoff that starts at 15 seconds and doubles each try ({{cite src/executor/dsh.ts:30}}, {{cite src/executor/dsh.ts:575}}). A host restart is different. It stops a running Assignment's shell jobs and subagents, then tells the Engine. The Engine restarts the Assignment with a recovery note. It skips the restart, and keeps the Session, only under two conditions. First, the last Report must already be waiting, ready, blocked or failed. Second, no later Input reached the worker after that Report ({{cite src/executor/dsh.ts:524-536}}, {{cite src/core/engine.ts:240-247}}, {{cite src/core/assignments.ts:83-90}}).

For the exact stage table, the retry and restart rules, and every execution variable a worker reads, see the repository's own {{cite docs/003-execution.md}}.

What can go wrong

A brand-new Ticket's first launch always reserves with by: 'launch'. It can wait behind a full set of normal slots even when a person is involved. Only a wake of an idle worker for that person's own message gets the extra slot ({{cite src/executor/dsh.ts:192-194}}, {{cite src/executor/dsh.ts:274}}).
  • A Ticket that looks finished may still hold a slot. Background jobs and subagents keep a worker's slot for up to 30 minutes after its turn ends. Counting slots by open Tickets alone can overstate how many are actually free ({{cite src/executor/dsh.ts:31-32}}, {{cite src/executor/dsh.ts:405-409}}).

This page leaves out the exact transient-retry backoff curve and the 10-minute workspace-prepare timeout. See the repository's own {{cite docs/003-execution.md}} for both.

Why it matters. Reading "3 of 3 slots used" as "3 Tickets are actively working" can be wrong. One of them may only be waiting on a background job after its own turn already ended.

What two things does the Executor give every accepted Ticket?

One Session, named worker-<ticket id>, and one directory under the execution root ({{cite src/executor/dsh.ts:23-24}}).

 Name the three methods the Engine calls on an Executor.

start(), deliver() and stop() ({{cite src/core/ports.ts:59-69}}).

 Can a Ticket's very first launch use the one extra worker slot kept for a person's message?

No. A launch always reserves with by: 'launch'; only a wake of an idle worker for a person's own message may use the extra slot ({{cite src/executor/dsh.ts:192-194}}, {{cite src/executor/dsh.ts:274}}).

 A worker's turn fails because of a provider timeout. Does its Assignment fail right away?

No. A transient provider or network failure is retried up to three times ({{cite src/executor/dsh.ts:548-553}}), with a backoff starting at 15 seconds and doubling each try ({{cite src/executor/dsh.ts:30}}, {{cite src/executor/dsh.ts:575}}).
