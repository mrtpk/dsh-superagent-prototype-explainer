The idea

A {{term source | Source}} is a plugin kind plus one configured instance, such as one GitHub repository ({{cite src/sources/kind.ts:85-115}}). It turns a native event into one Trigger: an immutable fact with its own actor, time and text. Every {{term trigger | Trigger}} names the {{term thread | Thread}} or Threads it belongs to, and a Thread is simply its Triggers in time order.

An everyday comparison. Think of a Source as a mail room. It turns an incoming letter into one tracking slip, a Trigger, filed under one case folder, a Thread. A reply leaves through the same slot, a {{term channel | Channel}}. The comparison stops here: one Thread can hold several open Tickets at once, which one physical folder cannot. A single native event can also belong to more than one Thread.

In the code

Step 1: a Source kind declares its shape; a Source instance configures one

Every installed Source implements the SourceKind contract: its configuration schema, its optional admission-table rows, and its outbound channel adapter ({{cite src/sources/kind.ts:85-113}}). GitHub and Feishu each register one instance of this contract ({{cite src/sources/github.ts:113}}, {{cite src/sources/feishu.ts:133}}). SourceRegistry.instance() resolves one SourceInstance for an installed kind ({{cite src/sources/registry.ts:50-53}}).

Step 2: a native event becomes a Trigger

commentTrigger() turns one GitHub comment into a Trigger. The Trigger names its Thread, its actor, whether a person wrote it, and whether it addressed the agent ({{cite src/sources/github-trigger.ts:65-77}}). The Trigger shape itself is Source-independent ({{cite src/core/model.ts:23-39}}); only meta carries Source-native details the core never reads.

Step 3: Triggers join a Thread, and a Subscription fans them out

Intake.receive() first checks whether the Source still listens to the event at all. One it does not listen to is stored with a filtered disposition and goes no further ({{cite src/core/intake.ts:25-29}}). A listened Trigger is then matched to every Thread it names, and fanned out to each Thread's subscribed Tickets as an Input ({{cite src/core/intake.ts:34-48}}). Only a Trigger no Ticket's worker decides is queued for a fresh {{term eval | Eval}} ({{cite src/core/intake.ts:58}}).

Step 4: a Channel is the Thread's write side

A Trigger can carry a channel: a Source, a Thread and an address in the Source's own format ({{cite src/core/model.ts:9}}). githubChannel() builds one from the Issue or pull-request number, and, for a review comment, its discussion URL.

SourceRegistry.send() hands an outgoing message to that Source kind's own channel.send() ({{cite src/sources/registry.ts:95-98}}). A Ticket collects the distinct Channels of the Triggers it was accepted from ({{cite src/core/tickets.ts:45-48}}).

More detail

What a Source instance listens to, and what else it observes, is its own configuration, not Policy's. GitHub's scope() reads one of four switches, such as receiving comments across the whole repository ({{cite src/sources/github.ts:59-62}}). It reports observed: true only for the scopes a person switched on. Intake.receive() calls this per-Source scope before a Trigger ever reaches a Thread ({{cite src/core/intake.ts:25-29}}). Whether that Trigger then becomes an explicit request, an inferred candidate, or nothing, is a separate, later question for {{link concepts/policy-and-authorization | Policy's gate}}.

A Trigger is deduplicated by id. Intake.receive() returns 'duplicate' at once for one already stored, before any filtering or fan-out runs ({{cite src/core/intake.ts:23}}). This is also why accepting the same native event twice cannot create two Tickets.

Fan-out adds a Trigger to a Ticket as an Input, with no Eval and no Decision ({{cite src/core/intake.ts:49-52}}). It grants the Ticket's Executor nothing beyond what the Ticket's existing {{term mandate | Mandate}} already allows. A Thread followed only for context marks its Input accordingly ({{cite src/core/intake.ts:42}}), and resumes no ended Ticket ({{cite src/core/intake.ts:43-44}}). See {{link concepts/policy-and-authorization}} for how that Mandate was granted in the first place.

For the full domain model, including Correlation, the relation between Threads that share a Trigger ({{cite src/core/model.ts:170}}), see the repository's own {{cite docs/001-domain.md}}.

What can go wrong

A Source that stopped listening to an event, such as a disabled Source or one whose scope excludes it, still stores the Trigger. But it has a filtered disposition and no Thread, Subscription fan-out, or Eval ({{cite src/core/intake.ts:25-29}}).
  • "Listened" and "admitted" are not the same check. A Source's own scope decides whether a Trigger enters the domain at all ({{cite src/core/intake.ts:25-29}}). Policy's gate separately decides, for a Trigger that did enter, whether it is explicit, inferred or ignored ({{link concepts/policy-and-authorization}}). Confusing the two can make a silent Source look like Policy is rejecting its messages.

This page leaves out Correlation, the relation between Threads that share a Trigger. It adds context only and never routes anything ({{cite src/core/model.ts:170}}).

Why it matters. Mixing up a Source's own scope with Policy's gate can hide a real admission problem behind what looks like a dead Source.

What does a Source turn one native event into?

One immutable Trigger, with its own actor, time, text and the Threads it belongs to ({{cite src/core/model.ts:23-39}}).

 What is a Thread, and can it hold more than one Ticket?

Triggers in time order. A Thread may carry several open Tickets at once ({{cite src/core/model.ts:157-182}}).

 What happens to a Trigger that its Source no longer listens to?

It is still stored, but with a filtered disposition: no Thread, no fan-out, no Eval ({{cite src/core/intake.ts:25-29}}).

 Does a Trigger reaching a Ticket through Subscription fan-out start a fresh Eval?

No. Intake.receive() adds it as an Input directly, with no Eval and no Decision; only a Trigger no Ticket's worker decides is queued for Eval ({{cite src/core/intake.ts:49-52}}, {{cite src/core/intake.ts:58}}).
