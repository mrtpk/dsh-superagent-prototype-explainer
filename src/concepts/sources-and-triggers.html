The idea

A {{term source | Source}} is a plugin kind plus one configured instance, such as one GitHub repository ({{cite src/sources/kind.ts:84-115}}). It turns a native event into one Trigger: an immutable fact with its own actor, time and text ({{cite src/core/model.ts:22-39}}). Every {{term trigger | Trigger}} names the {{term thread | Thread}} or Threads it belongs to. A Thread is its Triggers in time order. The Thread also holds its Subscriptions and its queue for the next Eval ({{cite src/core/model.ts:156-174}}).

An everyday comparison. Think of a Source as a mail room. It turns an incoming letter into one tracking slip, a Trigger, filed under one case folder, a Thread. A reply leaves through the same slot, a {{term channel | Channel}}. The comparison stops here: one Thread can hold several open Tickets at once, which one physical folder cannot ({{cite src/core/model.ts:163-164}}). A single native event can also belong to more than one Thread ({{cite src/core/model.ts:26-27}}).

In the code

Step 1: a Source kind declares its shape; a Source instance configures one

Every installed Source implements the SourceKind contract ({{cite src/sources/kind.ts:85-113}}). The contract has a configuration schema. Its optional parts include a scope rule, a Policy part with admission-table rows, and an outbound channel adapter ({{cite src/sources/kind.ts:37-38}}). The GitHub plugin and the Feishu plugin each register one Source kind ({{cite src/sources/github.ts:113}}, {{cite src/sources/feishu.ts:133}}). SourceRegistry.instance() resolves one SourceInstance for an installed kind ({{cite src/sources/registry.ts:50-53}}).

Step 2: a native event becomes a Trigger

commentTrigger() turns one GitHub comment into a Trigger. The Trigger names its Thread, its actor, whether a person wrote it, and whether it addressed the agent ({{cite src/sources/github-trigger.ts:65-77}}). The Trigger shape itself is Source-independent ({{cite src/core/model.ts:22-39}}). Only meta carries Source-native details, and the core never interprets them ({{cite src/core/model.ts:37-38}}).

Step 3: Triggers join a Thread, and a Subscription fans them out

Intake.receive() first drops a Trigger that it already stored ({{cite src/core/intake.ts:23}}). Then it checks whether the Source listens to the event. One it does not listen to is stored with a filtered disposition and goes no further ({{cite src/core/intake.ts:25-29}}). A listened Trigger is then matched to every Thread it names. It goes to each Thread's live subscribed Tickets as an Input ({{cite src/core/intake.ts:34-52}}). Only a Trigger no Ticket's worker decides is queued for a fresh {{term eval | Eval}} ({{cite src/core/intake.ts:58}}).

Step 4: a Channel is the Thread's write side

A Trigger can carry a channel: a Source, a Thread and an address in the Source's own format ({{cite src/core/model.ts:9}}). githubChannel() builds one from the Issue or pull-request number and, as an option, a comment URL. When the URL points at a review discussion comment, the reply goes to that review thread ({{cite src/sources/github-channel.ts:25-38}}).

SourceRegistry.send() hands an outgoing message to that Source kind's own channel.send() ({{cite src/sources/registry.ts:95-98}}). A Ticket collects the distinct Channels of the Triggers it was accepted from ({{cite src/core/tickets.ts:45-48}}).

More detail

What a Source instance listens to, and what else it observes, is its own configuration, not Policy's. GitHub's scope() always listens. It maps the event to one of four scopes and reads that scope's switch, such as receiving comments across the whole repository ({{cite src/sources/github.ts:30-37}}, {{cite src/sources/github.ts:59-62}}). It reports observed: true only for the scopes a person switched on. Intake.receive() calls this per-Source scope through the Source registry, before a Trigger reaches a Thread ({{cite src/core/intake.ts:25-29}}, {{cite src/sources/registry.ts:124-131}}). Whether that Trigger then becomes an explicit request, an inferred candidate, or nothing, is a separate, later question for {{link concepts/policy-and-authorization | Policy's gate}}.

A Trigger is deduplicated by id. Intake.receive() returns 'duplicate' at once for one already stored, before any filtering or fan-out runs ({{cite src/core/intake.ts:23}}). Thus the same native event, received twice, does not start a second Eval or a second Ticket.

Fan-out adds a Trigger to a Ticket as an Input, with no Eval and no Decision ({{cite src/core/intake.ts:49-52}}). It grants the Ticket's Executor nothing beyond what the Ticket's existing {{term mandate | Mandate}} already allows, because a Mandate never changes ({{cite src/core/model.ts:125}}). A Thread followed only for context marks its Input as context ({{cite src/core/intake.ts:42}}, {{cite src/core/intake.ts:51}}), and resumes no ended Ticket ({{cite src/core/intake.ts:43-44}}). See {{link concepts/policy-and-authorization}} for how that Mandate was granted in the first place.

For the full domain model, including Correlation, the relation between Threads that share a Trigger ({{cite src/core/model.ts:170-171}}), see the repository's own {{cite docs/001-domain.md}}.

What can go wrong

Intake still stores a Trigger that its Source does not listen to, for example from a disabled Source or from outside the Source's scope. But the Trigger has a filtered disposition and no Thread, Subscription fan-out, or Eval ({{cite src/core/intake.ts:25-29}}).
  • "Listened" and "admitted" are not the same check. A Source's own scope decides whether a Trigger enters the domain at all ({{cite src/core/intake.ts:25-29}}). Policy's gate separately decides, for a Trigger that did enter, whether it is explicit, inferred or ignored ({{link concepts/policy-and-authorization}}). If you mix up the two checks, a silent Source can look like a Policy that refuses its messages.

This page leaves out Correlation, the relation between Threads that share a Trigger. It adds context only and never routes anything ({{cite src/core/model.ts:170-171}}).

Why it matters. If you mix up a Source's own scope with Policy's gate, you look for the problem in the wrong place.

What does a Source turn one native event into?

One immutable Trigger, with its own actor, time, text and the Threads it belongs to ({{cite src/core/model.ts:22-39}}).

 What is a Thread, and can it hold more than one Ticket?

Triggers in time order. A Thread may carry several open Tickets at once, in its list of Subscriptions ({{cite src/core/model.ts:163-164}}).

 What happens to a Trigger that its Source no longer listens to?

It is still stored, but with a filtered disposition: no Thread, no fan-out, no Eval ({{cite src/core/intake.ts:25-29}}).

 Does a Trigger reaching a Ticket through Subscription fan-out start a fresh Eval?

No. Intake.receive() adds it as an Input directly, with no Eval and no Decision. Only a Trigger that no Ticket's worker decides is queued for Eval ({{cite src/core/intake.ts:49-52}}, {{cite src/core/intake.ts:58}}).
