The idea

dsh-superagent adds no page of its own. {{cite src/client/index.tsx:48-58}}'s apply() injects a sidebar icon and one main panel component into DSH's own slot system. The panel is an ordinary browser page. It never reads the Store or the Engine directly. It calls a small local HTTP API instead, under one path prefix: the {{term management-api | Management API}} ({{cite src/app/http.ts:230-246}}).

An everyday comparison. Think of the panel as a bank's teller window. It never touches the vault itself, only a counter where it hands over requests and gets answers back. The comparison stops at who else uses the counter. A second visitor here, the scripts/dsh-superagent command-line script, uses that same counter to check whether the service is healthy.

In the code

Step 1: one HTTP prefix, checked for loopback and same origin

registerHttp() refuses to start unless DSH's web server is bound to 127.0.0.1. It then serves every route under /orchestrator/api/ ({{cite src/app/http.ts:230-246}}). sameOrigin() adds two checks. The request's Host header must name that same loopback port. A marker header, x-orchestrator-request: 1, must be present ({{cite src/app/http.ts:74-78}}). The panel's own fetch helper sends exactly that header on every call ({{cite src/client/api.ts:33-37}}).

The panel never imports host code to do this. src/app/api.ts declares the whole route table as types only ({{cite src/app/api.ts:1}}, {{cite src/app/api.ts:20-45}}). The browser bundle carries the request and response shapes, but none of the server logic that produces them.

Step 2: six tabs, one concept per tab

{{cite src/client/route.ts:7}} fixes the six tabs: Overview, Source, Trigger, Eval, Execution and Settings. Pages() renders one view component per tab. Each reads its own slice of state, through the same typed call() helper ({{cite src/client/app.tsx:148-159}}).

Settings itself is five further groups, shown as one more level of tabs: Sources, Eval, Execution, Prompts and Deployment ({{cite src/client/route.ts:9}}). The Prompts group alone has three further views: Edit, Full prompt and History ({{cite src/client/prompts.tsx:13}}). That group is covered on {{link concepts/prompts-and-skills}}.

Step 3: a settings save versions against a block, not the whole object

Settings as a whole is one versioned record. It saves the same way as a {{term prompt-revision | prompt revision}}: each save stores a full numbered snapshot, and moves a pointer to it ({{cite src/app/versions.ts:21-28}}, {{cite src/app/store.ts:184-186}}). Each {{term settings-block | settings block}}, such as executor or one Source, also keeps its own separate counter ({{cite src/app/store.ts:188}}). So one page's save cannot be rejected by an unrelated page's edit.

Saving one block still re-checks for staleness after any async account check ({{cite src/app/settings.ts:166-168}}). This catches a save made elsewhere meanwhile. A no-op save, one whose merged value exactly equals the current settings, records no new revision at all ({{cite src/app/settings.ts:172-175}}).

Step 4: some fields only the panel itself may change

A settings save carries an origin: 'panel', 'tool' or, for policy, 'sync' ({{cite src/policy.ts:109}}). Two kinds of change are refused from any origin but 'panel'. One is the execution directory, prepare command or blocked-command list. The other is a Source's own account ({{cite src/app/settings.ts:44-45}}, {{cite src/app/settings.ts:50-51}}). This guards against a prompt-injected tool call changing what commands a worker may run. It is not an operating-system sandbox: a worker already runs ordinary shell commands.

More detail

GET state is the one route both the panel and the command-line script read. The panel polls it every 5 seconds by default ({{cite src/client/provider.tsx:74}}). It drops to 1-second polling while it detects a restart ({{cite src/client/provider.tsx:85-98}}). scripts/dsh-superagent status reads the same route once, with the same marker header ({{cite scripts/dsh-superagent:81-84}}). A write route such as PUT settings/:block or PUT prompts takes the revision it read back. The host then refuses a stale save with an HTTP 409, instead of silently overwriting someone else's change ({{cite src/app/http.ts:89}}).

One config knob changes how much a prompt configuration may hold: promptMaxChars, read fresh on every save rather than fixed at startup ({{cite src/app/http.ts:93-95}}). The Deployment settings group edits this same volatile field. dsh-superagent reads it again on each use, so a change applies without a restart ({{cite src/deployment.ts:14}}, {{cite src/deployment.ts:17}}).

An override records the key of the built-in text it was edited from. When that built-in text later changes, defaultChanged() compares the recorded key against the part's current built-in text ({{cite src/app/prompts.ts:186-194}}). A mismatch flags the part, with the old text when the host still has it saved. The panel's Prompts tab runs the same comparison on its own copy of the part ({{cite src/client/prompts.tsx:115-118}}). It shows a diff with exactly two buttons: keep the team's text, or take the new default ({{cite src/client/prompts.tsx:161-171}}). Neither button merges the two texts.

For the full list of settings groups, the panel's own guiding questions, and how search resolves a Feishu link, see the repository's own {{cite docs/005-panel.md}}.

What can go wrong

An empty 404 can come from DSH's own web server. This happens when dsh-superagent's routes are briefly unmounted during a restart, not when a record truly does not exist. The panel's own API client marks this case unreachable rather than missing ({{cite src/client/api.ts:49-55}}).
  • Reading two settings blocks, then saving one, can still conflict. That happens only if a third change lands on that same block in between. Staleness is checked per block, not per page load ({{cite src/app/settings.ts:150-151}}). The save fails even if the fields the panel edited were untouched.
  • A tool call cannot change the execution directory, blocked commands or a Source's account, whatever the request says. Only an origin of 'panel' may ({{cite src/app/settings.ts:44-45}}, {{cite src/app/settings.ts:50-51}}).

This page leaves out the exact fields of every settings group, and the full search syntax, such as a Feishu message id. See the repository's own {{cite docs/005-panel.md}}.

Why it matters. Treating every 404 as "this does not exist" can hide a restart in progress. Treating per-block versioning as whole-settings versioning can make an unrelated edit look like it caused a conflict.

How many tabs does the panel have, and what is the last one?

Six: Overview, Source, Trigger, Eval, Execution and Settings, with Settings last ({{cite src/client/route.ts:7}}).

 What header marks a request to the Management API as coming from the panel or the CLI script?

x-orchestrator-request: 1 ({{cite src/app/http.ts:74-78}}, {{cite scripts/dsh-superagent:81-84}}).

 Two people open the Execution tab and a Source's own settings tab at the same moment and each saves a change. Does the second save fail?

No, not because of the first save alone. executor and source:<id> are different settings blocks, each with its own revision counter ({{cite src/app/store.ts:188}}). A save fails only against a change to that same block.

 A tool call tries to change the execution directory. What stops it, and why is this not described as a sandbox?

executor's block guard throws unless the save's origin is 'panel' ({{cite src/app/settings.ts:44-45}}). The code's own comment calls this a guardrail against a prompt-injected tool call. It is not an OS security boundary: a worker already runs shell commands with full access ({{cite src/app/settings.ts:143}}).
