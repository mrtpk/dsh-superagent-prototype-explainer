This page follows one Ticket from accept to end, with the stage machine's own file and lines. scripts: viz/ticket-stage-stepper.js --- An accepted {{term ticket}} moves through a fixed set of {{term stage | stages}}, computed each time from its stored facts, mainly its latest {{term assignment | Assignment}} and Report.

The idea

A {{term ticket | Ticket}} keeps no stored status field. {{cite src/core/stage.ts:9-21}}'s ticketStage() computes the stage each time. It reads facts the Ticket already stores: its end, a failed delivery, an open Attention question, its latest {{term assignment | Assignment}}'s state, and that Assignment's {{term report | Report}}.

An everyday comparison. Think of a help-desk ticket with a status field someone sets by hand: "open", "waiting on customer", "closed". The comparison stops here. dsh-superagent's Ticket type has no such field ({{cite src/core/model.ts:277-308}}). Its stage is always derived, never stored. Thus the stage always agrees with the facts behind it.

In the code

Step 1: an accept creates the Ticket, its Mandate and its first Assignment

{{cite src/core/tickets.ts:37-56}}'s Tickets.create() builds the Ticket from the Eval's batch of Triggers. It collects the Channels of those Triggers ({{cite src/core/tickets.ts:45-48}}), then adds one pending Assignment before it saves the Ticket ({{cite src/core/tickets.ts:50-51}}).

The Ticket then subscribes to every Thread of the Eval's Triggers ({{cite src/core/tickets.ts:52}}) and asks the {{term executor | Executor}} to start that Assignment ({{cite src/core/tickets.ts:54}}).

Step 2: the stage machine reads what the Ticket already has

{{cite src/core/stage.ts:9-21}} checks conditions in a fixed order and returns the first match. The order is the same as in the panel-label table of {{cite docs/003-execution.md:9-17}}. The code adds one row before the table: an ended Ticket ({{cite src/core/stage.ts:10}}).

Line 17 is the one row that reads a second function, waitsForPerson() ({{cite src/core/model.ts:349-353}}). It stays true only until a newer human message reaches the Ticket, not a message from a context Thread. That is why a human reply lifts a Ticket off "Blocked" or "Failed".

Step 3: an Assignment moves from pending to running to ended

{{term assignment | Assignment}} has exactly three states ({{cite src/core/model.ts:211}}). Assignments.started() marks one running when the Executor reports that its launch started ({{cite src/core/assignments.ts:33-38}}). Tickets itself ends one directly, for example on a retry ({{cite src/core/tickets.ts:172}}, {{cite src/core/tickets.ts:387-390}}). The end of a Ticket ends all of its Assignments that did not end ({{cite src/core/tickets.ts:348}}, {{cite src/core/tickets.ts:358}}).

Step 4: a Subscription delivers later Triggers as Inputs, with no new Eval

{{cite src/core/intake.ts:34-48}} fans a stored Trigger out to every live Ticket subscribed to one of its Threads. A person's message can also reach an ended Ticket that a person did not stop, when the Thread is not a context Thread ({{cite src/core/intake.ts:40-44}}). For each Ticket reached, {{cite src/core/intake.ts:49-52}} adds the Trigger as an Input directly. {{term subscription | Subscription}} is the Thread's own list of subscribed Tickets ({{cite src/core/model.ts:163-164}}, {{cite src/core/tickets.ts:417-422}}). A message on a subscribed Thread reaches a Ticket this way with no Eval and no Decision. The message also goes to Eval only when no Ticket's worker decides it, for example a bot's message ({{cite src/core/intake.ts:56-58}}).

Intake.receive() then calls wake() on every reached Ticket ({{cite src/core/intake.ts:59}}). On a live Ticket this does nothing: wake() returns at once when the Ticket is not ended ({{cite src/core/tickets.ts:254}}). On an ended one, a person's message resumes it under the unchanged Mandate. This happens only when a person did not stop the Ticket, processing is not paused, and the current Policy still holds the Mandate ({{cite src/core/tickets.ts:254-257}}).

An Executor can follow a Thread for context without authority. Its messages still reach the Ticket, but grant it nothing and resume no ended Ticket ({{cite src/core/model.ts:165-169}}).

More detail

The stage machine, the Assignment lifecycle and Subscriptions meet at one shared field: the Ticket's latest Report. A worker's Report sets assignment.report directly ({{cite src/core/assignments.ts:122}}). {{cite src/core/stage.ts:9-21}} reads mainly that field to choose between Working, Awaiting review, Blocked and Failed. The same report decides whether the Ticket ends. A ready Report ends it as completed when the Ticket follows no Threads, such as a pull request. A dropped Report ends it too ({{cite src/core/assignments.ts:128-132}}).

One setting changes how long a Ticket waits in "Queued": the Executor's concurrency limit, maxWorkers. WorkerSlots reads it at each check ({{cite src/executor/dsh.ts:229-230}}). A wake for a person's message or a status request may use one slot beyond that limit ({{cite src/executor/dsh.ts:38}}, {{cite src/executor/dsh.ts:192-194}}, {{cite src/executor/dsh.ts:305-308}}). Thus new launches do not hold back a person's message to an idle worker.

Only an accept decision creates a Ticket ({{cite src/core/evals.ts:306-316}}). retry() ends the stalled Assignment and starts a new one on the same Ticket ({{cite src/core/tickets.ts:168-180}}). The Ticket keeps its worker Session id and its directory ({{cite src/executor/dsh.ts:24}}, {{cite src/core/model.ts:304-305}}). wake() resumes an ended Ticket when a person's message waits for it. It deletes the stored ended fact and starts a new Assignment, still under the Mandate the original accept granted ({{cite src/core/tickets.ts:252-270}}). Neither path asks Eval for a Decision, since nothing new needs authorizing.

For the stage table's exact panel labels and the delivery-retry timings this page leaves out, see the repository's own {{cite docs/003-execution.md}}.

What can go wrong

Check the Report state. Do not think that "no pull request" means that nothing happened. Assignments.report() ends the Ticket on a dropped Report exactly as it does on a completing ready Report ({{cite src/core/assignments.ts:128-132}}).
  • "Queued" and "Waiting for a Trigger" look similar but are not the same stage. Queued means the Ticket has no Assignment yet, or only a pending one ({{cite src/core/stage.ts:18}}). Idle means the latest Assignment already ended, or its last Report was "waiting" ({{cite src/core/stage.ts:19}}). A Queued Ticket waits for a launch. An idle Ticket waits for a new Trigger.

The stepper above leaves out the "ended" row ({{cite src/core/stage.ts:10}}) and the "person / delivery" row ({{cite src/core/stage.ts:11}}). It also leaves out the exact retry backoff timings. See the repository's own {{cite docs/003-execution.md}} for both.

Why it matters. If you read the wrong stage, a stalled Ticket can look healthy, or a healthy one can look stuck. Then a person can retry too late.

Does a Ticket store its own stage as a field, the way a help-desk ticket usually does?

No. Ticket has no stage field ({{cite src/core/model.ts:277-308}}); ticketStage() computes it each time from the Ticket's stored facts ({{cite src/core/stage.ts:9-21}}).

 What lifts a Ticket off "Blocked" or "Failed"?

A newer human message, or a retry. waitsForPerson() stays true only until a person's message reaches the Ticket after the latest Report ({{cite src/core/model.ts:349-353}}, read by {{cite src/core/stage.ts:17}}). A retry starts a new Assignment that has no Report yet ({{cite src/core/tickets.ts:168-180}}).

 Does a Subscription's fan-out trigger a fresh Eval on the Ticket it reaches?

No. {{cite src/core/intake.ts:49-52}} adds the Trigger straight onto the Ticket as an Input. Only a Trigger that no Ticket's worker decides is queued for Eval ({{cite src/core/intake.ts:58}}).

 Why do retry() and wake() never create a new Ticket, even though each starts a new Assignment?

Only an accept decision makes a Ticket id and creates a Ticket ({{cite src/core/evals.ts:311-314}}). retry() starts a new Assignment on the same Ticket ({{cite src/core/tickets.ts:168-180}}). wake() resumes an ended Ticket under its unchanged Mandate, with no new Eval or Decision ({{cite src/core/tickets.ts:252-270}}).
