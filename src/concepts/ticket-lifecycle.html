This page follows one Ticket from accept to end, with the stage machine's own file and lines. scripts: viz/ticket-stage-stepper.js --- An accepted {{term ticket}} moves through a fixed set of {{term stage | stages}}, computed fresh each time from its stored {{term assignment | Assignments}} and reports.

The idea

An open {{term ticket | Ticket}} keeps no stored status field. {{cite src/core/stage.ts:9-21}}'s ticketStage() computes one fresh each time. It reads facts the Ticket already stores: an open Attention question, its latest {{term assignment | Assignment}}'s state, and its latest {{term report | Report}}.

An everyday comparison. Think of a help-desk ticket with a status field someone sets by hand: "open", "waiting on customer", "closed". The comparison stops here. dsh-superagent's Ticket type has no such field ({{cite src/core/model.ts:277-308}}). Its stage is always derived, never stored, so it can never drift out of sync with the facts behind it.

In the code

Step 1: an accept creates the Ticket, its Mandate and its first Assignment

{{cite src/core/tickets.ts:32-38}}'s Tickets.create() builds the Ticket from the Eval's batch of Triggers. It collects the Channels of those Triggers ({{cite src/core/tickets.ts:45-48}}), then adds one pending Assignment before saving ({{cite src/core/tickets.ts:49-51}}).

The Ticket then subscribes to every Thread of the Eval's Triggers ({{cite src/core/tickets.ts:52}}) and asks the {{term executor | Executor}} to start that Assignment ({{cite src/core/tickets.ts:54}}).

Step 2: the stage machine reads what the Ticket already has

{{cite src/core/stage.ts:9-21}} checks conditions in a fixed order and returns the first match, exactly as the panel-label table of {{cite docs/003-execution.md:9-18}} lists them.

Line 17 is the one row that reads a second function, waitsForPerson() ({{cite src/core/model.ts:349-353}}). It stays true only until a newer human message arrives. That is why a human reply lifts a Ticket off "Blocked" or "Failed".

Step 3: an Assignment moves from pending to running to ended

{{term assignment | Assignment}} has exactly three states ({{cite src/core/model.ts:211}}). Assignments.started() marks one running once its Executor Session actually launches ({{cite src/core/assignments.ts:34-38}}); Tickets itself ends one directly, such as on a retry ({{cite src/core/tickets.ts:387-390}}).

Step 4: a Subscription delivers later Triggers as Inputs, with no new Eval

{{cite src/core/intake.ts:34-48}} fans a stored Trigger out to every Ticket subscribed to one of its Threads. For each one reached, {{cite src/core/intake.ts:49-52}} adds the Trigger as an Input directly. {{term subscription | Subscription}} is the Thread's own list of subscribed Tickets ({{cite src/core/tickets.ts:417-422}}). A message on a subscribed Thread reaches a Ticket this way with no Eval and no Decision.

Intake.receive() then calls wake() on every reached Ticket ({{cite src/core/intake.ts:59}}). On a live Ticket this does nothing: wake() returns at once when the Ticket is not ended ({{cite src/core/tickets.ts:254}}). On an ended one, a person's message resumes it under the unchanged Mandate.

An Executor can follow a Thread for context without authority. Its messages still reach the Ticket, but grant it nothing and resume no ended Ticket ({{cite src/core/model.ts:165-169}}).

More detail

The stage machine, the Assignment lifecycle and Subscriptions meet at one shared field: the Ticket's latest Report. A worker's Report sets assignment.report directly ({{cite src/core/assignments.ts:122}}), and that single field is almost everything {{cite src/core/stage.ts:9-21}} reads to choose between Working, Awaiting review, Blocked and Failed. The same report decides whether the Ticket ends. A ready Report with no pull request to wait for ends it as completed; a dropped Report ends it too ({{cite src/core/assignments.ts:128-132}}).

One config knob changes how long a Ticket waits in "Queued": the Executor's concurrency limit, maxWorkers. A worker slot reads it when reserved ({{cite src/executor/dsh.ts:229-230}}). A person's message or a status request may use one slot beyond that limit ({{cite src/executor/dsh.ts:192-194}}). So new proactive work can never block someone already talking to a Ticket.

Only an accept decision creates a Ticket ({{cite src/core/tickets.ts:32-38}}). retry() ends the stalled Assignment and starts a fresh one on the same Ticket, Session, directory and branch ({{cite src/core/tickets.ts:168-180}}). wake() resumes an ended Ticket when a person's message arrives. It deletes the stored ended fact and starts a new Assignment, still under the Mandate the original accept granted ({{cite src/core/tickets.ts:252-270}}). Neither path asks Eval for a Decision, since nothing new needs authorizing.

For the stage table's exact panel labels and the delivery-retry timings this page leaves out, see the repository's own {{cite docs/003-execution.md}}.

What can go wrong

Check the Report state before assuming "no pull request" means nothing happened. Assignments.report() ends the Ticket on a dropped Report exactly as it does on a completing ready Report ({{cite src/core/assignments.ts:128-132}}).
  • "Queued" and "Waiting for a Trigger" look similar but are not the same stage. Queued means the Ticket has no Assignment yet, or only a pending one ({{cite src/core/stage.ts:18}}). Idle means the latest Assignment already ended, or its last Report was "waiting" ({{cite src/core/stage.ts:19}}). Confusing the two misreads whether a worker slot is in use.

The stepper above leaves out the stage table's first row, "person / delivery" ({{cite src/core/stage.ts:11}}). It also leaves out the exact retry backoff timings. See the repository's own {{cite docs/003-execution.md}} for both.

Why it matters. Reading the wrong stage can make a stalled Ticket look fine, or a healthy one look stuck, which delays a person's retry.

Does a Ticket store its own stage as a field, the way a help-desk ticket usually does?

No. Ticket has no stage field ({{cite src/core/model.ts:277-308}}); ticketStage() computes it fresh every time from the Ticket's stored facts ({{cite src/core/stage.ts:9-21}}).

 What lifts a Ticket off "Blocked" or "Failed"?

A newer human message. waitsForPerson() stays true only until one arrives after the latest Report ({{cite src/core/model.ts:349-353}}, read by {{cite src/core/stage.ts:17}}).

 Does a Subscription's fan-out trigger a fresh Eval on the Ticket it reaches?

No. {{cite src/core/intake.ts:34-48}} adds the Trigger straight onto the Ticket as an Input; only a Trigger that no Ticket's worker decides is queued for Eval ({{cite src/core/intake.ts:58}}).

 Why do retry() and wake() never create a new Ticket, even though each starts a new Assignment?

Only an accept decision creates a Ticket id ({{cite src/core/tickets.ts:32-38}}). retry() starts a new Assignment on the same Ticket ({{cite src/core/tickets.ts:168-180}}). wake() resumes an ended Ticket under its unchanged Mandate, with no new Eval or Decision ({{cite src/core/tickets.ts:252-270}}).
