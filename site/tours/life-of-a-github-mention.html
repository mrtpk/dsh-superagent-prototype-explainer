Life of a GitHub mention: from a comment to a merged pull request

IntermediateGuided toursabout 10 min read + 1 min deep dives

Code version: dsh-superagent @ 6337fc8 · 2026-10-31

Before you read

This page uses ideas from these pages:

  • What dsh-superagent is Beginner
  • Source, Trigger, Thread and Channel: where work comes from Intermediate

In one sentence

An allowed person mentions the agent in a GitHub comment, and the comment becomes a Ticket, a pull request and, eventually, a closed Ticket.

The idea#

This tour follows one real path through the system map on the home page: a comment that mentions dsh-superagent's GitHub account. Every stop below names the file and the function the reader is in, with the exact lines.

An everyday comparison. Think of an email that reaches a busy person's inbox. Someone checks whether the sender may ask for this kind of work, and decides to accept it. Only then do they start, reply and, at the end, close it. The comparison stops at the gate: dsh-superagent's check is a written rule in code, not a person's judgment.

The picture#

Read each panel left to right. The three parts match this tour's stops in groups: stops 1-7 build the Ticket, stops 8-11 do the work, and stops 12-13 end the Ticket.

1A GitHub comment mentions the agent#

The GitHub Source reads the comment in a poll, and turns it into a Trigger. mentions() matches @login only as a whole name, and ignores upper and lower case.

For a mention, the notification poll reads the Issue or pull request that GitHub names (src/sources/github.ts:344-372). It calls intakeComments(), which reads the comments since the Thread's cursor and passes each to ctx.receive() (src/sources/github.ts:384-402). The poll of a subscribed Thread also calls intakeComments() (src/sources/github.ts:452-457).

2Intake ingests the Trigger#

Intake.receive() normalizes the timestamp, rejects a duplicate id, and checks the Source's scope before the Trigger enters the domain.

Because no Ticket yet subscribes to this comment's Thread, the fan-out loop reaches none (src/core/intake.ts:34-48), and the Trigger is queued for Eval (src/core/intake.ts:58).

3The gate admits it as explicit#

Before Eval batches anything, the active Policy's gate decides the strength of every queued Trigger on the Thread. For a human Trigger, an allowed sender who addressed the agent is always explicit.

src/core/evals.ts:96 calls this gate once per queued Trigger when Evals.start() runs on the Thread.

4Eval batches the Thread and asks the assessor#

Evals.start() takes every Trigger still queued on the Thread, keeps the strongest admissible one, and opens one Eval for the whole batch.

assessor.request() enqueues an assessment effect. Its handler delivers the candidate card to the main Session (src/app/assessment.ts:96-104). This happens for an explicit candidate too. But the assessment tools orchestrator_eval and orchestrator_eval_read refuse an explicit candidate. Their error tells the main Session to route it with orchestrator_route (src/app/assessment.ts:39, src/app/assessment.ts:109-113). docs/002-authorization.md:85 gives the same rule.

5The main Session routes an accept#

orchestrator_route lets the main Session decide several candidates in one call. Each item runs as its own Engine command, so one refused item never blocks the others.

engine.decide() records a Decision. Only an accept Decision makes a Ticket. Any other Decision becomes the item's refusal (line 100).

src/app/tools/main.ts:125-153 defines the tool itself: up to 20 decisions per call, each answered on its own (src/app/tools/main.ts:129).

6Eval's accept builds the Mandate and asks for a Ticket#

Evals.decide() routes the accept outcome to accept(), which builds the Mandate the new Ticket will carry.

The Ticket's id comes from the Eval's own id (src/core/evals.ts:311). Thus one Eval maps to one Ticket id. Evals.decide() also returns the earlier Decision when a Trigger already made a Ticket (src/core/evals.ts:136-146).

7Tickets.create() builds the Ticket and starts the Executor#

Tickets.create() does four things in one call. It builds the Ticket and its first Assignment. It subscribes the Ticket to every Thread of the Eval's Triggers. It queues the accept's acknowledgement, when the accept has one, and asks the Executor to start.

Ticket creation is covered in full on The Ticket lifecycle: stages, Assignments and Subscriptions. This tour only follows the one path this mention takes.

8The acknowledgement goes back to GitHub#

Because the comment's Trigger is human and has a Channel, the accept's acknowledgement is queued for delivery before the worker even starts.

The Outbox records a receipt and enqueues a durable reply effect in the same transaction (src/app/outbox.ts:27-32). Later, sendGithub() posts the comment under the agent's account. A hidden marker in the comment lets a retry find the earlier post, so the retry does not post it again (src/sources/github-channel.ts:34-39).

9The Executor launches the worker Session#

DshExecutor.start() only enqueues a launch effect; the actual launch runs once a worker slot is free.

launch() prepares the Ticket's workspace directory on first use (src/executor/dsh.ts:434-438), then sends the first message with the Ticket's assignment text and the originating Trigger (src/executor/dsh.ts:449-466).

Deep dive

What if every worker slot is already busy?

A launch only runs once WorkerSlots.reserve() grants it a slot (src/executor/dsh.ts:192-194). The limit comes from the Executor's maxWorkers setting (src/executor/dsh.ts:229-230). Until then, the Assignment stays pending, and the panel shows the Ticket as "Queued" (src/core/stage.ts:18, docs/003-execution.md:15). A launch never gets an extra slot. A wake of an idle worker for a person's message, or for a status request, may use one extra slot beyond the limit (src/executor/dsh.ts:38, src/executor/dsh.ts:305-308). Thus a busy deployment can still answer a person who talks to an existing Ticket.

10The worker Session works, and opens a pull request#

The worker reads its assignment and the Ticket's execution variables. They name the repository, the agent's GitHub account, and the Issue or pull request that started the Ticket.

The worker gets these variables as a list in its system prompt, not as shell variables (src/app/sessions.ts:247, src/app/prompts.ts:83-84). dsh-superagent knows a pull request of the worker by its author and its branch name. The agent account must be the author, and the branch's last path segment must match the Ticket's short name (src/sources/github-pull.ts:23-28). docs/003-execution.md:53 describes the same contract.

11The worker reports ready, naming its pull request#

orchestrator_report is how a worker tells its Ticket what happened. Naming a pr_number claims that pull request for the Ticket in the same call.

claimPull() accepts only the Ticket's own source PR, or an agent-authored PR on the Ticket's branch, and refuses a PR another open Ticket already claims (src/sources/github-pull.ts:35-49).

12The report is recorded; the Ticket waits for review#

Assignments.report() stores the worker's report on the Assignment, and decides whether this report ends the Ticket.

With an open pull request still followed, this ready report leaves the Ticket open, in the stage person / review (src/core/stage.ts:15). The panel calls this stage "Awaiting review" (docs/003-execution.md:13).

13GitHub observes the pull request close, and the Ticket ends#

Each poll round reads the open pull requests that open Tickets follow (src/sources/github.ts:404-409). Once a pull request is closed or merged, observePull() reports it to the Tickets that follow it.

Tickets.threadClosed() marks the follow closed. It ends the Ticket when followsDone() holds and no taken-up work is unfinished (src/core/tickets.ts:77-89, src/core/tickets.ts:345-362). followsDone() holds once every pull request that the Ticket opened is closed. For a Ticket that opened none, every followed Thread must close (src/core/tickets.ts:95-100). GitHub already shows the merge or close on the pull request itself, so the final notice this Ticket would otherwise send skips its GitHub Channels (src/sources/github-pull.ts:102-104).

What can go wrong#

A ready report does not always end the Ticket

Check whether the Ticket still follows an open pull request before reading a ready report as finished work. src/core/assignments.ts:128-132 ends the Ticket only once followsDone() has an outcome, which an open, followed pull request does not yet have.

  • An inferred mention would not take this path. This tour assumes an allowed sender's explicit mention. A person not on the allowed list, or a comment that does not mention the agent, takes the admission-table path instead (src/policy.ts:198-210). An inferred candidate from that path becomes a Ticket only in auto mode (docs/002-authorization.md:91-101).
  • A later comment by a person on the same Thread does not repeat this tour. Once the Thread's Ticket exists, the Trigger reaches it through its Subscription (src/core/intake.ts:34-52). The Ticket owns the Trigger, so it gets no new Eval (src/core/intake.ts:56-58). A bot's comment still goes to Eval (src/core/model.ts:76).

Why it matters. Do not read every comment as a new "mention to Ticket" run. Only the first request on a Thread takes this full path. The worker decides a later comment by a person, not the gate.

Check yourself#

  1. 1
    Which function decides that an allowed person's mention is explicit, not inferred?
    easy
    Show answer

    The Policy's gate, src/policy.ts:191-211. Line 197 returns explicit strength once an allowed sender's Trigger is addressed.

  2. 2
    Does the acknowledgement reply wait for the worker to start?
    easy
    Show answer

    No. src/core/tickets.ts:49-56 queues the acknowledgement in the same call that creates the Ticket, before the Executor's launch even reaches a worker slot.

  3. 3
    How does dsh-superagent know a pull request belongs to this Ticket, if the worker opened it itself?
    medium
    Show answer

    By its branch name. src/sources/github-pull.ts:27-28's ticketBranch() matches the branch's last path segment against the Ticket's short name, which claimPull() then checks when the worker reports it (src/sources/github-pull.ts:35-49).

  4. 4
    A worker reports ready with an open pull request it is still following. Does the Ticket end?
    hard
    Show answer

    No. src/core/assignments.ts:128-132 only ends the Ticket once followsDone() gives it an outcome. That needs every pull request the Ticket opened to be closed first. For a Ticket that opened none, every followed Thread must close (src/core/tickets.ts:95-100). The Ticket ends later, once GitHub reports the close (src/core/tickets.ts:77-89).
