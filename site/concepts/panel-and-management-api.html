The panel and the Management API: tabs, routes and settings versions

Intermediatedsh-superagent conceptsabout 8 min read + 1 min deep dives

Code version: dsh-superagent @ 6337fc8 · 2026-10-31

Before you read

This page uses ideas from these pages:

  • What dsh-superagent is Beginner
  • The Ticket lifecycle: stages, Assignments and Subscriptions Intermediate

In one sentence

A React panel injected into DSH's web sidebar calls a loopback-only Management API, and every save versions against a number.

The idea#

dsh-superagent adds no page of its own. src/client/index.tsx:49-58's apply() injects a sidebar icon, one main panel component and a Plugin Manager config view into DSH's own slot system. The panel is an ordinary browser page. It never reads the Store or the Engine directly. It calls a small local HTTP API instead, under one path prefix: the Management API (src/app/http.ts:230-246).

An everyday comparison. Think of the panel as a bank's teller window. It never touches the vault itself, only a counter where it hands over requests and gets answers back. The comparison stops at who else uses the counter. A second visitor here, the scripts/dsh-superagent command-line script, uses that same counter to check whether the service is healthy.

The picture#

Read panel 1 left to right: the panel's own fetch call, the API, and the host state behind it. Panel 2 lists the six tabs in their fixed order. Panel 3 shows the two checks a save passes before it is accepted.

In the code#

Step 1: one HTTP prefix, checked for loopback and same origin#

registerHttp() refuses to start unless DSH's web server is bound to 127.0.0.1. It then serves every route under /orchestrator/api/ (src/app/http.ts:230-246). sameOrigin() adds three checks. The request's Host header must name 127.0.0.1 or localhost at that same port. A marker header, x-orchestrator-request: 1, must be present. An Origin header, if present, must match the host (src/app/http.ts:75-79). The panel's own fetch helper sends exactly that header on every call (src/client/api.ts:33-37).

The panel never imports host code to do this. src/app/api.ts declares the whole route table as types only (src/app/api.ts:1, src/app/api.ts:20-45). The browser bundle carries the request and response shapes, but none of the server logic that produces them.

Step 2: six tabs, one concept per tab#

src/client/route.ts:7 fixes the six tabs: Overview, Source, Trigger, Eval, Execution and Settings. Pages() renders one view component per tab (src/client/app.tsx:147-159). The repository's own docs list what each tab shows (docs/005-panel.md:17-24).

Settings has five groups: Sources, Eval, Execution, Prompts and Deployment (src/client/route.ts:9). The Prompts group alone has three further views: Edit, Full prompt and History (src/client/prompts.tsx:13). That group is covered on Prompts and Source skills: how the system prompt is assembled.

Step 3: a settings save versions against a block, not the whole object#

Settings as a whole is one versioned record. It saves the same way as a prompt revision: each save stores a full numbered snapshot, and moves a pointer to it (src/app/versions.ts:21-28, src/app/store.ts:184-186). Each settings block, such as executor or one Source, also keeps its own separate counter (src/app/store.ts:188). So an edit to one block does not make a save of another block fail.

A block save checks its revision again after the async model and account checks (src/app/settings.ts:162-168). This catches a save of the same block that another caller made in that time. A no-op save, one whose merged value exactly equals the current settings, records no new revision at all (src/app/settings.ts:172-175).

Step 4: some fields only the panel itself may change#

A settings save carries an origin: 'panel', 'tool' or, for policy, 'sync' (src/policy.ts:109). Two kinds of change are refused from any origin but 'panel'. One is a change to the execution directory, the prepare command or the blocked-command list (src/app/settings.ts:23-24, src/app/settings.ts:44-45). The other is a change to a Source's account fields (src/app/settings.ts:50-51). The code calls this a guardrail against a prompt-injected tool call. It is not an operating-system security boundary, because agents run shell commands (src/app/settings.ts:143).

More detail#

GET state is the one route both the panel and the command-line script read. The panel polls it every 5 seconds by default (src/client/provider.tsx:74, src/client/provider.tsx:89). After a save or a setup check that restarts the host, it polls every second. It stops this when the server went down and answers again, or after 30 seconds (src/client/provider.tsx:85-98). scripts/dsh-superagent status reads the same route once, with the same marker header (scripts/dsh-superagent:81-84, scripts/dsh-superagent:122-124). A write route such as PUT settings/:block or PUT prompts takes the revision that the caller read (src/app/http.ts:149, src/app/http.ts:209). The host refuses a stale save with an HTTP 409. It does not overwrite the other change (src/app/http.ts:89).

One config knob changes how much a prompt configuration may hold: promptMaxChars. Prompts reads it again for each check, not once at startup (src/app/runtime.ts:103, src/app/prompts.ts:178-179). The Deployment settings group shows and edits this volatile field (src/client/deployment.tsx:77, src/app/http.ts:93-95). dsh-superagent reads it again on each use, so a change applies without a restart (src/deployment.ts:14, src/deployment.ts:17-18).

Deep dive

Why a prompt upgrade needs a human choice, not a silent merge

An override records the key of the built-in text it was edited from. When that built-in text later changes, defaultChanged() compares the recorded key against the part's current built-in text (src/app/prompts.ts:186-194). A mismatch flags the part, with the old text when the host still has it saved. The panel's Prompts tab runs the same comparison on its own copy of the part (src/client/prompts.tsx:115-118). It shows a diff with exactly two buttons: keep the team's text, or take the new default (src/client/prompts.tsx:161-171). Neither button merges the two texts.

For the full list of settings groups, the panel's own guiding questions, and how search resolves a Feishu link, see the repository's own docs/005-panel.md.

What can go wrong#

A 404 from the Management API does not always mean the record is missing

An empty 404 can come from DSH's own web server. This happens when dsh-superagent's routes are briefly unmounted during a restart, not when a record truly does not exist. The panel's own API client marks this case unreachable, so missing stays false (src/client/api.ts:22-23, src/client/api.ts:49-55).

  • Reading two settings blocks, then saving one, can still conflict. That happens only if a third change lands on that same block in between. Staleness is checked per block, not per page load (src/app/settings.ts:150-151). The save fails even if the fields the panel edited were untouched.
  • A tool call cannot change the execution directory, blocked commands or a Source's account, whatever the request says. Only an origin of 'panel' may (src/app/settings.ts:44-45, src/app/settings.ts:50-51).

Simplified

This page leaves out the exact fields of every settings group, and the full search syntax, such as a Feishu message id. See the repository's own docs/005-panel.md.

Why it matters. Treating every 404 as "this does not exist" can hide a restart in progress. Treating per-block versioning as whole-settings versioning can make an unrelated edit look like it caused a conflict.

    No, not because of the first save alone. executor and source:<id> are different settings blocks, each with its own revision counter (src/client/execution.tsx:81, src/app/store.ts:188). A save fails only against a change to that same block.
