Source, Trigger, Thread and Channel: where work comes from

Intermediatedsh-superagent conceptsabout 6 min read + 1 min deep dives

Code version: dsh-superagent @ 6337fc8 · 2026-10-31

Before you read

This page uses ideas from these pages:

  • What dsh-superagent is Beginner

In one sentence

A Source turns a native event into an immutable Trigger; Triggers in time order form a Thread, and a Channel writes the reply back.

The idea#

A Source is a plugin kind plus one configured instance, such as one GitHub repository (src/sources/kind.ts:84-115). It turns a native event into one Trigger: an immutable fact with its own actor, time and text (src/core/model.ts:22-39). Every Trigger names the Thread or Threads it belongs to. A Thread is its Triggers in time order. The Thread also holds its Subscriptions and its queue for the next Eval (src/core/model.ts:156-174).

An everyday comparison. Think of a Source as a mail room. It turns an incoming letter into one tracking slip, a Trigger, filed under one case folder, a Thread. A reply leaves through the same slot, a Channel. The comparison stops here: one Thread can hold several open Tickets at once, which one physical folder cannot (src/core/model.ts:163-164). A single native event can also belong to more than one Thread (src/core/model.ts:26-27).

Read each panel left to right. Panel 1 shows how one GitHub comment becomes a Trigger on a Thread. Panel 2 shows how the reply goes out through the Trigger's Channel, back to the same Source.

In the code#

Step 1: a Source kind declares its shape; a Source instance configures one#

Every installed Source implements the SourceKind contract (src/sources/kind.ts:85-113). The contract has a configuration schema. Its optional parts include a scope rule, a Policy part with admission-table rows, and an outbound channel adapter (src/sources/kind.ts:37-38). The GitHub plugin and the Feishu plugin each register one Source kind (src/sources/github.ts:113, src/sources/feishu.ts:133). SourceRegistry.instance() resolves one SourceInstance for an installed kind (src/sources/registry.ts:50-53).

Step 2: a native event becomes a Trigger#

commentTrigger() turns one GitHub comment into a Trigger. The Trigger names its Thread, its actor, whether a person wrote it, and whether it addressed the agent (src/sources/github-trigger.ts:65-77). The Trigger shape itself is Source-independent (src/core/model.ts:22-39). Only meta carries Source-native details, and the core never interprets them (src/core/model.ts:37-38).

Step 3: Triggers join a Thread, and a Subscription fans them out#

Intake.receive() first drops a Trigger that it already stored (src/core/intake.ts:23). Then it checks whether the Source listens to the event. One it does not listen to is stored with a filtered disposition and goes no further (src/core/intake.ts:25-29). A listened Trigger is then matched to every Thread it names. It goes to each Thread's live subscribed Tickets as an Input (src/core/intake.ts:34-52). Only a Trigger no Ticket's worker decides is queued for a fresh Eval (src/core/intake.ts:58).

Step 4: a Channel is the Thread's write side#

A Trigger can carry a channel: a Source, a Thread and an address in the Source's own format (src/core/model.ts:9). githubChannel() builds one from the Issue or pull-request number and, as an option, a comment URL. When the URL points at a review discussion comment, the reply goes to that review thread (src/sources/github-channel.ts:25-38).

SourceRegistry.send() hands an outgoing message to that Source kind's own channel.send() (src/sources/registry.ts:95-98). A Ticket collects the distinct Channels of the Triggers it was accepted from (src/core/tickets.ts:45-48).

More detail#

What a Source instance listens to, and what else it observes, is its own configuration, not Policy's. GitHub's scope() always listens. It maps the event to one of four scopes and reads that scope's switch, such as receiving comments across the whole repository (src/sources/github.ts:30-37, src/sources/github.ts:59-62). It reports observed: true only for the scopes a person switched on. Intake.receive() calls this per-Source scope through the Source registry, before a Trigger reaches a Thread (src/core/intake.ts:25-29, src/sources/registry.ts:124-131). Whether that Trigger then becomes an explicit request, an inferred candidate, or nothing, is a separate, later question for Policy's gate.

A Trigger is deduplicated by id. Intake.receive() returns 'duplicate' at once for one already stored, before any filtering or fan-out runs (src/core/intake.ts:23). Thus the same native event, received twice, does not start a second Eval or a second Ticket.

Deep dive

What reaching a Ticket does, and does not, grant

Fan-out adds a Trigger to a Ticket as an Input, with no Eval and no Decision (src/core/intake.ts:49-52). It grants the Ticket's Executor nothing beyond what the Ticket's existing Mandate already allows, because a Mandate never changes (src/core/model.ts:125). A Thread followed only for context marks its Input as context (src/core/intake.ts:42, src/core/intake.ts:51), and resumes no ended Ticket (src/core/intake.ts:43-44). See Policy and authorization: the gate, Eval and the Mandate it grants for how that Mandate was granted in the first place.

For the full domain model, including Correlation, the relation between Threads that share a Trigger (src/core/model.ts:170-171), see the repository's own docs/001-domain.md.

What can go wrong#

A filtered Trigger never reaches a Thread

Intake still stores a Trigger that its Source does not listen to, for example from a disabled Source or from outside the Source's scope. But the Trigger has a filtered disposition and no Thread, Subscription fan-out, or Eval (src/core/intake.ts:25-29).

  • "Listened" and "admitted" are not the same check. A Source's own scope decides whether a Trigger enters the domain at all (src/core/intake.ts:25-29). Policy's gate separately decides, for a Trigger that did enter, whether it is explicit, inferred or ignored (Policy and authorization: the gate, Eval and the Mandate it grants). If you mix up the two checks, a silent Source can look like a Policy that refuses its messages.

Simplified

This page leaves out Correlation, the relation between Threads that share a Trigger. It adds context only and never routes anything (src/core/model.ts:170-171).

Why it matters. If you mix up a Source's own scope with Policy's gate, you look for the problem in the wrong place.

Check yourself#

  1. 1
    What does a Source turn one native event into?
    easy
    Show answer

    One immutable Trigger, with its own actor, time, text and the Threads it belongs to (src/core/model.ts:22-39).

  2. 2
    What is a Thread, and can it hold more than one Ticket?
    easy
    Show answer

    Triggers in time order. A Thread may carry several open Tickets at once, in its list of Subscriptions (src/core/model.ts:163-164).

  3. 3
    What happens to a Trigger that its Source no longer listens to?
    medium
    Show answer

    It is still stored, but with a filtered disposition: no Thread, no fan-out, no Eval (src/core/intake.ts:25-29).

  4. 4
    Does a Trigger reaching a Ticket through Subscription fan-out start a fresh Eval?
    hard
    Show answer

    No. Intake.receive() adds it as an Input directly, with no Eval and no Decision. Only a Trigger that no Ticket's worker decides is queued for Eval (src/core/intake.ts:49-52, src/core/intake.ts:58).
