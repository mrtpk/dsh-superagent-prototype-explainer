What dsh-superagent is

BeginnerLearn the basicsabout 8 min read + 1 min deep dives

Code version: dsh-superagent @ 6337fc8 · 2026-10-31

Before you read

You do not need to read other pages first.

In one sentence

dsh-superagent is a proactive coding agent for one GitHub repository, built as a DSH bundle that runs on Cordis.

The idea#

When an allowed person asks dsh-superagent for work, it opens a Ticket. It works on the Ticket in its own agent Session and directory, and it answers in the original conversation (README.md:7). Its guiding rule is to take as little human attention as possible, and give as much value as possible (docs/000-philosophy.md:5). It acts only when a person asks, or when a rule that the team wrote allows it. It speaks only when a person must act or can use a result (README.md:9).

An everyday comparison. Think of a new teammate who speaks up only when asked and works alone at their own desk. They report back in the same conversation where the request came from. The comparison stops at authorization. A human teammate uses judgment, but a written Policy decides who may ask dsh-superagent for work (src/core/ports.ts:16-20). The agent does not use its own judgment for this.

In dsh-superagent#

What the sibling site already teaches#

This site assumes you already know DSH and Cordis from the sibling site, DeepSeek Harness Explained. It does not re-teach them; each line below only recaps and names the matching page there.

  • Cordis plugins. In DeepSeek Harness, every part is a plugin on Cordis. A plugin claims services from a shared context, and plugins tell each other about events. See the sibling site's page "Everything is a plugin: Cordis".
  • Profiles and bundles. A DSH profile stacks named bundles, then patch files overlay the result, to assemble one running DSH tree. dsh-superagent is one such bundle. See "Profiles and bundles".
  • The session vocabulary. A DSH session counts its own work with four words: turn, step, round and exchange. See "Turn, step, round: the session vocabulary".
  • Skills. A skill is one full instruction body that a session loads on demand from a shared catalog. See "Skills".
  • Jobs and background work. A background job, a workflow script, a durable goal and plan mode are optional capabilities beside the turn/step loop. See "Jobs, workflows, goals and plan mode".

What dsh-superagent adds#

Source and Trigger. A Source is a stream of events, such as the GitHub Source (src/sources/github.ts:38-64). Each event becomes one immutable Trigger, with its own Threads and, where relevant, a Channel to reply on (src/core/model.ts:22-39). Source, Trigger, Thread and Channel: where work comes from covers all four.

Policy and Eval. A Policy is the versioned rule set that decides who may start work. A gate checks each Trigger against it, and Eval turns an admissible batch into a Decision (src/core/ports.ts:17-27, src/core/evals.ts:21-26). An accept Decision carries a Mandate: the strength, scope and Policy version the work relies on (src/core/model.ts:125-133). Policy and authorization: the gate, Eval and the Mandate it grants covers all five.

Ticket. Only an accept Decision creates a Ticket (src/core/evals.ts:306-316). The Ticket has no stored status field (src/core/model.ts:277-308). Its stage is computed each time from its stored facts, mainly its latest Assignment and that Assignment's Report (src/core/stage.ts:9-21). The Ticket lifecycle: stages, Assignments and Subscriptions follows one Ticket from accept to end.

Executor. The Executor is the port that runs a Ticket's Assignments (src/core/ports.ts:55-69). dsh-superagent's own implementation keeps one worker Session and one directory for each Ticket (src/executor/dsh.ts:1). It runs that Session inside DSH, under a worker slot limit (src/executor/dsh.ts:201-207). The Executor and worker Sessions: one Session per Ticket, a concurrency limit covers it, and Effects and the Store: a durable queue, and one writer per state covers the durable queue and Store behind it.

The panel. A React panel opens from an icon in DSH's web sidebar (src/client/index.tsx:49-55). It shows what needs a person (README.md:7). A local Management API serves its data (src/app/http.ts:230-237). The panel and the Management API: tabs, routes and settings versions covers both, and Prompts and Source skills: how the system prompt is assembled covers the prompts the Executor and the main Session read.

More detail#

One Trigger's path through these parts runs in a fixed order.

  1. Intake stores the Trigger, checks the Source's scope, and fans the Trigger out to subscribed Tickets (src/core/intake.ts:19-62).
  2. When no Ticket's worker decides the Trigger, it goes to Eval. The gate decides its strength (src/core/intake.ts:58, src/policy.ts:191-211).
  3. Eval batches the Thread's queued Triggers into one Decision (src/core/evals.ts:71-119).
  4. An accept Decision builds the Mandate and the Ticket (src/core/evals.ts:306-316, src/core/tickets.ts:37-56).
  5. The Executor queues a launch of a worker Session (src/executor/dsh.ts:263-266). A reply goes out through a Channel (src/app/outbox.ts:26-32).

A later Trigger on a Thread that a live Ticket subscribes to reaches the Ticket as a new Input through its Subscription (src/core/intake.ts:34-52). When the Ticket's worker decides a person's message, the message goes to no Eval. A bot's message goes to Eval too (src/core/intake.ts:56-58).

Two settings change this path's behaviour the most. The Policy's accept mode is off, observe or auto (src/core/model.ts:103). It decides whether an inferred candidate can become a Ticket. The gate marks a candidate inferred when it is not an explicit request. Only auto lets an assessment accept an inferred candidate, and only on enabled rules that the assessment matched (src/policy.ts:212). The Executor's maxWorkers limit decides how many worker Sessions can run at once (src/executor/dsh.ts:229-230). A wake for a person's message can use one extra slot (src/executor/dsh.ts:192-194).

Deep dive

Why GitHub and Feishu share one Source contract

GitHub and Feishu are two different Source kinds. Both implement the same SourceKind contract (src/sources/kind.ts:85-100). The contract has a configuration schema. Its optional parts include a scope function that decides what the Source listens to, and a channel to reply on. Policy and Eval never see a Source's own vocabulary, such as a Feishu chat or a GitHub Issue. They see only Triggers, Threads and Channels. This is why Source, Trigger, Thread and Channel: where work comes from explains one shared model, instead of one page per Source.

For the full domain model and why each concept exists, see the repository's own docs/001-domain.md.

What can go wrong#

Do not expect a GitHub Issue, a Feishu chat or a model call anywhere in the domain model

Source, Trigger, Policy, Eval, Ticket and Executor are deliberately abstract. A business need becomes an attribute of one of them, or prompt text, never a new concept (docs/001-domain.md:3, docs/001-domain.md:39). Do not look for a Feishu-specific rule in the domain layer. Look in the Feishu Source and in the prompts.

  • "Executor" and "worker" are not interchangeable with "Ticket." The Executor is the port that runs the work; the worker is its Session, named worker-<ticket id> (src/executor/dsh.ts:24). A Ticket itself is never called a worker.
  • The main Session is not a Ticket's worker. Code and prompts name the two roles orchestrator and worker (src/app/prompts.ts:46). The main Session evaluates Triggers, accepts and dispatches Tickets, and replies (docs/001-domain.md:80-81). Only an Executor Session does the ticketed work itself.

Why it matters. If you mix up these roles, you can look for a Ticket's own behaviour in the Executor's code. You can also make the opposite mistake.

Check yourself#

  1. 1
    Does dsh-superagent re-implement Cordis plugins or DSH profiles itself?
    easy
    Show answer

    No. It runs as one DSH bundle, a set of Cordis plugins that a DSH profile loads (cordis.patch.yml:4-12). Cordis and DSH profiles are the sibling site's own territory.

  2. 2
    Which concept does only an accept Decision ever create?
    easy
    Show answer

    A Ticket. Tickets.create() (src/core/tickets.ts:37-56) has one caller, Evals.accept() (src/core/evals.ts:306-316).

  3. 3
    A person writes a later GitHub comment on a Thread that a live Ticket subscribes to. Does the comment go through the gate and Eval again?
    medium
    Show answer

    No, when the Ticket's worker decides the comment. src/core/intake.ts:34-52 fans it out to the subscribed Ticket directly, as a new Input, with no new Eval or Decision. Only a Trigger that no Ticket's worker decides goes to Eval (src/core/intake.ts:58).

  4. 4
    Why does the domain model have no Feishu-specific or GitHub-specific concept?
    hard
    Show answer

    Every Source implements one shared contract, src/sources/kind.ts:85-100: Policy and Eval only ever see Triggers, Threads and Channels. A business need specific to one Source becomes an attribute of that Source, or prompt text, never a new domain concept (docs/001-domain.md:3, docs/001-domain.md:39).
